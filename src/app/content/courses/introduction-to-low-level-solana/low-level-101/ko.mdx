# 로우 레벨 101 (Low-level 101)

![Low-level 101](/graphics/banners/research-crateless-program.png)

Solana 프로그램을 작성해 본 적이 있다면, Entrypoint, CPI, 계정 관리와 같은 프로그램의 모든 기본 요구 사항은 일반적으로 `solana_program` 및 `pinocchio`와 같은 크레이트에서 처리된다는 것을 알고 있을 것입니다. 이러한 크레이트는 anchor, steel과 같은 프레임워크 내부에서 사용됩니다.

하지만 Solana 스택을 진정으로 이해하고 최적화하려면 이러한 모든 추상화 뒤에 숨겨진 내용을 살펴보고 내부에서 무슨 일이 일어나는지 확인해야 합니다. 이 코스에서는 처음부터 의존성이 없는(zero-dependency) 완전히 직접 작성한(hand-rolled) Solana 프로그램을 만들 것입니다.

다양한 직접 작성한 구성 요소를 살펴보기 전에 Solana 프로그램을 작동하게 하는 기본 구성 요소를 이해해야 합니다.

<ArticleSection name="eBPF" id="eBPF" level="h2" />

Solana 프로그램은 네이티브 기계 코드가 아닌 eBPF(extended Berkeley Packet Filter) 바이트코드로 컴파일됩니다. 이러한 아키텍처 선택은 많은 Solana의 특징을 설명합니다:
- **컴퓨팅 단위 제한 (Compute unit limits)**: eBPF의 안전 모델은 명령어를 계산하여 무한 루프를 방지합니다.
- **힙 할당 없음 (No heap allocation)**: eBPF 프로그램은 malloc/free 없이 샌드박스 환경에서 실행됩니다.
- **제한된 스택 (Limited stack)**: 4KB의 스택 공간만 있어 신중한 메모리 관리가 필요합니다.
- **결정론적 실행 (Deterministic execution)**: 동일한 입력은 모든 검증인에서 항상 동일한 출력을 생성합니다.

이것이 특정 Rust 기능이 Solana 프로그램에서 작동하지 않는 이유를 설명합니다. 런타임이 말 그대로 실행할 수 없기 때문입니다.

<ArticleSection name="#[repr(C)] & extern `C`" id="repr-c-and-extern-c" level="h2" />

로우 레벨 Solana 예제를 보면 두 가지 패턴이 어디에서나 나타납니다:

```rust
#[repr(C)]              
pub struct MyState { … }

pub unsafe extern "C" fn entrypoint(ptr: *mut u8) -> u64 { … }
```

**`extern "C"`**

Rust 컴파일러에게 C ABI(Application Binary Interface)를 사용하여 함수를 노출하도록 지시합니다. 이는 어떤 eBPF 레지스터가 인수를 전달하고, 스택이 어떻게 배치되며, 어떤 레지스터가 값을 반환하는지 정의하는 호출 규칙입니다.

C ABI가 선택된 이유는 LLVM의 eBPF 백엔드가 지원하는 모든 언어(Rust, C, Zig 또는 직접 작성한 어셈블리)에서 가장 낮은 공통 분모이기 때문입니다. Solana 런타임은 프로그램의 진입점을 원시 이름으로 호출하고 특정 레지스터를 통해 매개변수를 전달해야 합니다. C ABI는 어떤 언어가 바이트코드를 컴파일했는지에 관계없이 이것이 작동하도록 보장합니다.

**`#[repr(C)]`** 

Rust가 C 컴파일러처럼 구조체 필드를 배열하도록 강제하여 필드 순서와 패딩을 잠그므로 바이트 레이아웃이 절대 변경되지 않도록 합니다:

```rust
// #[repr(C)] 없음 - Rust는 최적화를 위해 필드를 재정렬할 수 있습니다!
struct UnpredictableState {
    amount: u64,     // 오프셋 0, 8 또는 16에 있을 수 있음
    owner: [u8; 32], // 위치는 컴파일러 기분에 따라 다름
    bump: u8,        // 아무 곳에나 패킹되거나 패딩될 수 있음
}

// #[repr(C)] 있음 - 레이아웃이 보장되고 예측 가능함
#[repr(C)]
struct PredictableState {
    amount: u64,     // 항상 오프셋 0
    owner: [u8; 32], // 항상 오프셋 8  
    bump: u8,        // 항상 오프셋 40
    // 암시적 패딩: 8바이트 경계에 맞추기 위한 7바이트
}
```

이것은 계정 데이터가 프로그램 호출 간에 유지되기 때문에 중요합니다. Rust가 컴파일 간에 필드를 재정렬하면 프로그램은 이전에 쓴 데이터를 읽을 수 없게 됩니다.

<ArticleSection name="메모리 레이아웃 관리" id="memory-layout-management" level="h2" />

고수준 프레임워크에서는 메모리 정렬이 자동으로 이루어집니다. 로우 레벨에서는 모든 바이트가 중요합니다:

```rust
#[repr(C)]
struct BadAlignment {
    flag: u8,        // 1바이트
    // 컴파일러가 여기에 7바이트의 패딩을 삽입합니다
    amount: u64,     // 8바이트 - 8바이트 정렬 필요!
    owner: [u8; 32], // 32바이트
} // 합계: 48바이트 (41바이트 아님!)

#[repr(C)]  
struct GoodAlignment {
    amount: u64,     // 8바이트 - 자연적으로 정렬됨
    owner: [u8; 32], // 32바이트  
    flag: u8,        // 1바이트
    // 끝에 7바이트의 패딩만 있음
} // 합계: 48바이트, 하지만 패딩이 예측 가능함
```

메모리 관리 규칙은 각 필드가 자신의 크기로 나누어 떨어지는 오프셋에서 시작해야 한다는 것입니다:
- `u8`: 모든 오프셋 (1로 나누어 떨어짐)
- `u16`: 오프셋은 2로 나누어 떨어져야 함 (0, 2, 4...)
- `u32`: 오프셋은 4로 나누어 떨어져야 함 (0, 4, 8...)
- `u64`: 오프셋은 8로 나누어 떨어져야 함 (0, 8, 16...)

메모리를 잘못 관리하면 잘못 정렬된 메모리 액세스로 이어져 프로그램이 예측할 수 없게 실패할 수 있기 때문에 이것은 정말 중요합니다.

계정 데이터 직렬화를 수동으로 관리할 때 패딩과 정렬을 이해하는 것은 프로그램 간 호환성을 위해 중요합니다.

#### Syscalls 

**시스템 호출(System call)** 또는 syscall은 권한이 없는 코드가 호스트에게 권한 있는 서비스를 요청하는 통로입니다. syscall이 이루어지면 CPU는 사용자 모드에서 신뢰할 수 있는 권한 모드로 전환됩니다. 그런 다음 런타임은 요청된 작업을 수행하고 상태 코드와 함께 제어를 반환합니다. 이러한 간접화는 샌드박스 코드가 호스트 메모리나 I/O를 직접 건드리는 것을 방지하여 안전과 결정론을 보존합니다.

Solana에서 BPF 바이트코드는 자체적으로 해싱, 로깅 또는 프로그램 간 호출(CPI)을 수행할 수 없습니다. 대신 `sol_log`, `sol_sha256`, `sol_invoke_signed`와 같은 명명된 syscall을 호출합니다.

각 syscall 번호는 단순히 로더의 디스패치 테이블에 있는 인덱스입니다. 로더는 요청된 작업을 수행하고 `u64` 상태 워드(성공 시 0, 실패 시 0이 아님)를 반환합니다.

예를 들어, `sol_invoke_signed`는 명령어, 계정 목록 및 모든 PDA 서명자 시드를 패키징하여 로더에 전달하고, 로더는 다음과 같이 적절한 권한으로 CPI를 수행합니다:

```rust
/// 서명된 명령어를 호출하기 위한 Solana BPF syscall.
fn sol_invoke_signed_c(
    instruction_addr: *const u8,
    account_infos_addr: *const u8,
    account_infos_len: u64,
    signers_seeds_addr: *const u8,
    signers_seeds_len: u64,
) -> u64;
```

<ArticleSection name="볼트 코드" id="the-vault-code" level="h2" />

이제 "crateless" Solana 프로그램의 모든 구성 요소를 분석했으므로 볼트 자체를 개략적으로 설명할 수 있습니다. 기억하세요, 볼트는 정확히 두 가지 작업을 수행합니다:
- 소유자의 공개 키에서 파생된 PDA에 Lamport를 **예치(Deposit)**합니다.
- 나중에 동일한 Lamport를 **인출(Withdraw)**합니다. 소유자만 가능합니다.

따라서 각 명령어는 세 개의 계정을 전달합니다:
- **소유자(Owner)** (서명자, 쓰기 가능): 자금을 예치하거나 인출하는 사용자.
- **볼트(Vault)** (쓰기 가능): 모든 Lamport가 포함된 PDA.
- **시스템 프로그램(System Program)**: Lamport 이체를 수행하는 데 필요한 계정.

시작하기 전에 새 프로젝트를 만들어야 합니다. 터미널에서 다음 명령을 실행하세요:

```
# 워크스페이스 생성
cargo new blueshift_vault --lib --edition 2021
cd blueshift_vault
```

`Cargo.toml`에 다음을 추가하세요:

```
[lib]
crate-type = ["lib", "cdylib"]
```

#### 계정 확인 (Account Checks)

`deposit` 또는 `withdraw`를 실행하기 전에 진입점은 트랜잭션이 정확히 올바른 계정을 제공했는지, 각 계정에 예상되는 플래그가 있는지 확인해야 합니다.

원시 포인터 수준에서 작업하고 있으므로 모든 확인은 간단한 포인터 산술 및 직접 로드로 수행됩니다.

입력 레코드의 처음 8바이트는 account_len을 보유합니다. 이 볼트의 경우 소유자, 볼트 PDA 및 시스템 프로그램의 세 가지 계정을 예상합니다:

```rust
// 3개의 계정(서명자, 볼트, 프로그램)이 있는지 확인
if *(input as *const u64) != 3 {
    sol_log_("Invalid number of accounts".as_ptr(), 26);
    return 1010; // NotEnoughAccountKeys Error
}
```

각 계정을 확인하며 계속 진행합니다. 앞서 정의한 레이아웃 오프셋을 사용하면 전체 구조체를 역직렬화하지 않고도 모든 플래그를 정합성 검사할 수 있습니다.

첫 번째 계정인 서명자의 경우 수행하는 검사는 다음과 같습니다:
- 고유해야 함 (is_duplicate == 0xff)
- 쓰기 가능 (Lamport를 변경할 것이므로)
- 서명자
- 실행 불가능
- 데이터가 없어야 함

```rust
if *(input.add(ACCOUNT_OFFSET) as *const u32) != 0x0101ff {
    sol_log_("Invalid Account 1 Data: Non-Duplicate, Writable, Signer, Non-Executable Check Failed".as_ptr(), 58);
    return 1003; // InvalidAccountData Error
}
if *(input.add(ACCOUNT_OFFSET + DATA_LEN_OFFSET) as *const usize) != 0 {
    sol_log_("Invalid Account 1 Data: Data Length is not 0".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}
```

또한 나중에 PDA 확인을 위해 소유자의 공개 키를 보관합니다:

```rust
let signer_key = *(input.add(ACCOUNT_OFFSET + KEY_OFFSET) as *const [u8; 32]);
```

두 번째 계정인 볼트의 경우 수행하는 검사는 다음과 같습니다:
- 쓰기 가능 (Lamport를 변경할 것이므로)
- 시스템 프로그램 소유
- 데이터 길이는 0이어야 함 (여기에 상태를 저장하지 않음)

```rust
const ACCOUNT_2_OFFSET: usize = ACCOUNT_OFFSET + ACCOUNT_RAW_LEN;

if *(input.add(ACCOUNT_2_OFFSET + IS_WRITABLE_OFFSET) as *const u8) != 1 {
    sol_log_("Invalid Account 2 Data: Writable Check Failed".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}

if *(input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as *const [u8; 32]) != pinocchio_system::ID {
    sol_log_("Invalid Account 2 Data: Owner is not the System Program".as_ptr(), 48);
    return 1022; // InvalidAccountOwner Error
}

if *(input.add(ACCOUNT_2_OFFSET + DATA_LEN_OFFSET) as *const usize) != 0 {
    sol_log_("Invalid Account 2 Data: Data Length is not 0".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}
```

또한 나중에 PDA 확인을 위해 볼트의 공개 키를 가져옵니다:

```rust
let vault_key = *(input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as *const [u8; 32]);
```

마지막 계정인 시스템 프로그램의 경우 수행하는 검사는 다음과 같습니다:
- 실행 가능해야 함
- 키는 SYSTEM_PROGRAM_ID와 같아야 함

```rust
const ACCOUNT_3_OFFSET: usize = ACCOUNT_2_OFFSET + ACCOUNT_RAW_LEN;
const SYSTEM_PROGRAM_DATA_LENGTH: usize = 14 + 2;

if *(input.add(ACCOUNT_3_OFFSET + EXECUTABLE_OFFSET) as *const u8) != 1 {
    sol_log_("Invalid Account 3 Data: Executable Check Failed".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}

if *(input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as *const [u8; 32]) != SYSTEM_PROGRAM_ID {
    sol_log_("Invalid Account 3 Data: Owner is not the System Program".as_ptr(), 48);
    return 1003; // InvalidAccountData Error
}
```

#### 명령어 확인 (Instruction checks)

계정 검증 후 마침내 명령어 페이로드를 구문 분석할 수 있습니다. 그리고 첫 번째 바이트를 구별자로 사용하여 네이티브 프로그램과 동일한 접근 방식을 취합니다:

```rust
const INSTRUCTION_OFFSET: usize = ACCOUNT_3_OFFSET + ACCOUNT_RAW_LEN + SYSTEM_PROGRAM_DATA_LENGTH + INSTRUCTION_LEN_LEN;

let discriminator = *(input.add(INSTRUCTION_OFFSET) as *const u8);
match discriminator {
    0 => {
        sol_log_("Deposit".as_ptr(), 7);

        // deposit 로직 …

        return 0; // Success
    }
    1 => {
        sol_log_("Withdraw".as_ptr(), 8);

        // withdraw 로직 …

        return 0; // Success
    }
    _ => {
        sol_log_("Invalid Instruction".as_ptr(), 20);
        return 1002; // InvalidInstructionData Error
    }
}
```

여기서 우리는 모든 계정과 플래그가 정확히 볼트가 예상하는 것임을 확신하며 예치 또는 인출 핸들러로 분기합니다.

#### 예치 로직 (Deposit Logic)

예치 명령어에 대한 더 자세한 설명과 함께 시작하겠습니다. 모든 확인은 맨 앞에 있습니다. 통과하면 시스템 프로그램 전송을 작성하고 호출합니다.

이 명령어의 명령어 데이터는 다음과 같습니다:
- 바이트 0은 구별자(예치의 경우 `0x00`).
- 바이트 1은 PDA 확인에 재사용할 범프.
- 바이트 2-9는 리틀 엔디안의 Lamport 양을 보유하며 0이면 거부됩니다.

```rust
let amount = *(input.add(INSTRUCTION_OFFSET + 2) as *const u64);
if amount == 0 {
    return 1002; // InvalidInstructionData Error
}
```

그 후 범프, 프로그램 ID 및 고유 문자열 "ProgramDerivedAddress"를 사용하여 소유자 키를 해시합니다(`sol_sha256` syscall 사용).

계정 확인 중에 보관한 볼트 키와 결과를 비교합니다. 다르면 `InvalidSeeds`를 반환합니다.

```rust
let bump: u8 = *(input.add(INSTRUCTION_OFFSET + 1) as *const u8);
let data = [
    signer_key.as_ref(),
    &[bump],
    ID.as_ref(),
    b"ProgramDerivedAddress",
];

let mut pda = core::mem::MaybeUninit::<[u8; 32]>::uninit();
sol_sha256(
    &data as *const _ as *const u8,
    4,
    pda.as_mut_ptr(),
);

if vault_key != *pda.as_ptr() {
    sol_log_("Invalid PDA address".as_ptr(), 19);
    return 1013; // InvalidSeeds Error
};
```

마지막으로 시스템 프로그램 전송을 작성할 수 있습니다.

시스템 프로그램은 4바이트 구별자(전송의 경우 값은 2)를 사용하고 `from_account`에서 `to_account`로 전송하려는 양을 나타내는 추가 8바이트가 필요합니다.

그런 다음 두 개의 SolAccountMeta 값(from = owner (서명자, 쓰기 가능), to = vault (쓰기 가능))의 작은 배열을 빌드해야 합니다. `instruction_data`와 결합하여 `SolInstruction` 구조체를 생성합니다:

```rust
let mut instruction_data = [0; 12];
instruction_data[0] = 2; // discriminator
instruction_data[4..12].copy_from_slice(&amount.to_le_bytes()); // amount

let accounts_addr: [SolAccountMeta; 2] = [
    // from_account
    SolAccountMeta { 
        pubkey_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: true,
    },
    // to_account
    SolAccountMeta { 
        pubkey_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: false,
    },
];

// 명령어 생성
let instruction = SolInstruction {
    program_id_addr: input.add(ACCOUNT_3_OFFSET + KEY_OFFSET) as u64,
    accounts_addr: accounts_addr.as_ptr() as u64,
    accounts_len: 2,
    data_addr: instruction_data.as_ptr() as u64,
    data_len: 12,
};
```

하지만 `sol_invoke_signed_c` syscall을 호출하기 전에 소유자와 볼트에 대해 하나씩, 로더가 메모리에 남겨둔 Lamport 잔고 및 데이터 슬라이스에 대한 포인터를 제공하는 두 개의 `SolAccountInfo` 구조체를 빌드해야 합니다.

그 후 명령어 포인터, 두 요소 `SolAccountInfo` 배열에 대한 포인터 및 계정 수(2)를 전달하여 syscall을 호출할 수 있습니다. 외부 트랜잭션은 이미 소유자에 의해 서명되었으므로 여기서는 PDA 시드가 필요하지 않으므로 `signers_seeds_addr` 인수는 NULL입니다.

```rust
let account_infos_addr: [SolAccountInfo; 2] = [
    SolAccountInfo {
        is_signer: true,
        is_writable: true,
        executable: false,
        key_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        lamports_addr: input.add(ACCOUNT_OFFSET + LAMPORTS_OFFSET) as u64,
        data_len: 0,
        data_addr: input.add(ACCOUNT_OFFSET + DATA_OFFSET) as u64,
        owner_addr: input.add(ACCOUNT_OFFSET + OWNER_OFFSET) as u64,
        rent_epoch: 0,
    },
    SolAccountInfo {
        is_signer: false,
        is_writable: true,
        executable: false,
        key_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        lamports_addr: input.add(ACCOUNT_2_OFFSET + LAMPORTS_OFFSET) as u64,
        data_len: 0,
        data_addr: input.add(ACCOUNT_2_OFFSET + DATA_OFFSET) as u64,
        owner_addr: input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as u64,
        rent_epoch: 0,
    },
];

// 서명자 시드로 명령어 호출
sol_invoke_signed_c(
    &instruction as *const SolInstruction as *const u8,
    account_infos_addr.as_ptr() as *const u8,
    2, // 계정 수
    core::ptr::null(),
    0,
);
```

#### 인출 로직 (Withdraw Logic)

인출 명령어는 예치와 유사하지만 몇 가지 주요 차이점이 있습니다. 명령어 데이터는 더 간단합니다:
- 바이트 0은 구별자(인출의 경우 `0x01`).
- 바이트 1은 PDA 확인에 재사용할 범프.

```rust
let bump: u8 = *(input.add(INSTRUCTION_OFFSET + 1) as *const u8);
```

소유자의 공개 키, 범프, 프로그램 ID 및 고유 문자열 "ProgramDerivedAddress"를 사용하여 예치와 동일한 PDA 확인을 수행합니다:

```rust
let data = [
    signer_key.as_ref(),
    &[bump],
    ID.as_ref(),
    b"ProgramDerivedAddress",
];

let mut pda = core::mem::MaybeUninit::<[u8; 32]>::uninit();
sol_sha256(
    &data as *const _ as *const u8,
    4,
    pda.as_mut_ptr(),
);

if vault_key != *pda.as_ptr() {
    sol_log_("Invalid PDA address".as_ptr(), 19);
    return 1013; // InvalidSeeds Error
};
```

인출의 주요 차이점은 PDA 자체로 트랜잭션에 서명해야 한다는 것입니다. 이를 위해 PDA를 파생하는 데 사용된 시드를 제공해야 합니다. 두 요소가 있는 `SolSignerSeedsC` 배열을 만듭니다:
- 소유자의 공개 키 (32바이트)
- 범프 (1바이트)

```rust
let seeds: [SolSignerSeedsC; 2] = [
    SolSignerSeedsC {
        addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        len: 32,
    },
    SolSignerSeedsC {
        addr: input.add(INSTRUCTION_OFFSET + 1) as u64,
        len: 1,
    },
];

let signer_seeds_addr: [SolSignerSeedsC; 1] = [
    SolSignerSeedsC {
        addr: seeds.as_ptr() as u64,
        len: 2,
    },
];
```

그런 다음 시스템 프로그램 전송 명령어를 작성하지만 이번에는 볼트에서 소유자에게로 전송합니다. 명령어 데이터는 예치와 동일합니다:
- 4바이트 구별자 (전송의 경우 값 2)
- 양에 대한 8바이트 (볼트의 Lamport에서 가져옴)

```rust
let amount = *(input.add(ACCOUNT_2_OFFSET + LAMPORTS_OFFSET) as *const u64);

let mut instruction_data = [0; 12];
instruction_data[0] = 2;
instruction_data[4..12].copy_from_slice(&amount.to_le_bytes());
```

계정 메타는 예치와 비교하여 반전됩니다:
- 첫 번째 계정은 볼트 (쓰기 가능, 서명자)
- 두 번째 계정은 소유자 (쓰기 가능)

```rust
let account_addr: [SolAccountMeta; 2] = [
    SolAccountMeta {
        pubkey_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: true,
    },
    SolAccountMeta {
        pubkey_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: false,
    },
];
```

마지막으로 `sol_invoke_signed_c`를 명령어, 계정 정보 및 앞서 생성한 서명자 시드와 함께 호출합니다:

```rust
sol_invoke_signed_c(
    &instruction as *const SolInstruction as *const u8,
    account_infos_addr.as_ptr() as *const u8,
    2, // 계정 수
    signer_seeds_addr.as_ptr() as *const u8,
    1,
);
```

<ArticleSection name="맺음말" id="closing-remarks" level="h2" />

Solana 프로그램을 작성하는 이 로우 레벨 접근 방식은 극단적으로 보일 수 있지만 중요한 교육적 목적을 수행합니다. 우리는 이런 식으로 프로그램을 작성하라고 제안하는 것이 아닙니다. 사실, 이러한 복잡성을 추상화하는 확립된 프레임워크와 크레이트를 사용하는 것을 강력히 권장합니다. 그러나 기본 메커니즘을 이해하는 것은 매우 귀중합니다.

`solana_program`, `anchor` 또는 기타 프레임워크이든 Solana 개발에서 사용하는 모든 추상화는 이러한 기본 구성 요소 위에 구축됩니다. 층을 벗겨내고 원시 메커니즘을 검토함으로써 다음을 더 깊이 이해할 수 있습니다:

1. Solana 런타임이 프로그램과 상호 작용하는 방식
2. 고수준 프레임워크에서 특정 설계 결정이 내려진 이유
3. 잠재적 최적화가 존재할 수 있는 곳
4. 문제가 발생했을 때 문제를 더 잘 디버깅하는 방법

이 지식은 단지 학문적인 것이 아니라 실용적입니다. 기초를 이해하면 다음을 수행할 수 있습니다:
- 데이터 구조 및 메모리 사용에 대한 정보에 입각한 결정을 내려 더 효율적인 프로그램을 작성
- 문제가 발생했을 때 더 잘 진단하고 수정
- 우리 모두가 사용하는 도구를 개선하여 생태계에 기여
- 특정 추상화를 사용할 때와 메탈에 더 가깝게 작업할 때를 결정

기억하세요, 이 연습의 목표는 크레이트 없이 프로그램을 작성하는 방법을 가르치는 것이 아니라 해당 크레이트가 내부에서 무엇을 하고 있는지 이해하도록 돕는 것입니다. 이러한 이해는 어떤 도구를 사용하든 더 좋고 효율적인 Solana 프로그램을 작성하기 위한 첫 걸음입니다.
