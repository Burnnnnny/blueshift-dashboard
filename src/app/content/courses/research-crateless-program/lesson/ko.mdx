# 바이트 단위로: Crate 없는 프로그램의 해부 (Byte by Byte: The Anatomy of a Crateless Program)

![Image Test](/graphics/banners/research-crateless-program.png)

Solana 프로그램을 작성해 본 적이 있다면 분명 `solana_program`, `pinocchio`와 같은 crate를 사용했거나 `anchor`, `steel`과 같이 이러한 crate를 내부적으로 사용하는 프레임워크를 사용했을 것입니다...

하지만 이러한 crate가 존재하지 않는다면 무엇을 해야 할지 궁금해한 적이 있나요? 완전히 수동으로 작성된 crate 없는 Solana 프로그램을 만들 로우 레벨 101에 오신 것을 환영합니다.

<ArticleSection name="로우 레벨 Solana 101" id="low-level-solana-101" level="h2" />

소매를 걷어붙이고 전체 볼트 예제를 수동으로 작성하기 전에, Solana 프로그램에 대한 몇 가지 기본 사항을 이해해야 합니다.

#### `[repr(C)]` 및 `extern C`

로우 레벨 Solana 예제를 보면 두 가지 패턴이 계속해서 나타납니다:

```rust
#[repr(C)]              
pub struct MyState { … }

pub unsafe extern "C" fn entrypoint(ptr: *mut u8) -> u64 { … }
```

- `extern "C"`는 Rust 컴파일러에게 C ABI를 따르는 심볼을 노출(또는 기대)하도록 지시합니다. C ABI는 어떤 eBPF 레지스터가 인수를 전달하고, 스택이 어떻게 배치되며, 어떤 레지스터가 값을 반환하는지 정의하는 호출 규칙입니다.
- `#[repr(C)]`는 Rust가 C 컴파일러와 정확히 동일하게 구조체를 배열하도록 강제하여 필드 순서와 패딩을 잠가 바이트 레이아웃이 절대 변경되지 않도록 합니다.

왜 C ABI가 선택되었을까요? LLVM의 eBPF 백엔드가 지원하는 모든 언어(Rust, C, Zig 또는 수동으로 작성된 어셈블리)에서 가장 낮은 공통 분모이기 때문입니다. 어떤 도구 모음이 바이트코드를 생성하든 Solana 런타임은 프로그램의 진입 함수를 원시 이름으로 호출하고 세 개의 포인터를 올바른 레지스터에 밀어 넣어야 합니다. C ABI를 고수하면 모든 LLVM 기반 언어에서 생성된 코드에 대해 작동할 것이 보장됩니다.

#### 진입점 (Entrypoint)

`entrypoint!()`는 모든 Solana 프로그램이 노출해야 하는 단일 심볼입니다. Solana 런타임이 로더에서 코드로 점프하는 핸드오프 지점입니다.

점프하기 전에 로더는 명령어에 필요한 모든 것을 BPF VM의 입력 페이지에 저장된 하나의 평면 C 스타일 레코드로 압축합니다. 그런 다음 매크로는 해당 레코드의 압축을 풀고 Rust에 세 가지 안전한 슬라이스와 참조를 전달합니다:
- **program_id**: 현재 실행 중인 프로그램의 공개 키입니다.
- **accounts**: AccountInfo 레코드의 연속 배열에 대한 포인터와 길이입니다.
- **instruction_data**: 트랜잭션에서 제공하는 원시 바이트의 포인터 플러스 길이 슬라이스입니다.

매크로는 다음을 수행합니다:
- 해당 원시 포인터를 안전한 Rust 슬라이스로 변환합니다.
- 패닉을 포착하여 VM을 중단시키는 대신 깨끗한 `ProgramError::Custom` 코드가 되도록 합니다.
- 모든 것을 `ProgramResult`를 반환하는 사용자 정의 함수(종종 `process_instruction`이라고 함)로 전달합니다.

Solana 로더가 진입점으로 점프하기 전에 BPF VM의 입력 페이지에 배치하는 단일 평면 레코드에 대한 설명은 다음과 같습니다.

```rust
pub struct Entrypoint {
    account_len: u64,
    account_info: [AccountRaw; account_len]
    instruction_len: u64,
    instruction_data: [u8; instruction_len]
    program_id: [u8; 32],
}
```
- `account_len`: 전송된 계정의 수입니다.
- `account_info`: 명령어의 원시 계정 레코드로, 하나씩 차례로 나옵니다.
- `instruction_len`: 다음에 오는 명령어 데이터의 바이트 수입니다.
- `instruction_data`: 명령어 자체입니다.
- `program_id`: 실행 중인 프로그램의 32바이트 `Pubkey`입니다.

`account_info` 배열의 모든 요소는 동일한 압축 레이아웃을 따릅니다:

```rust
pub struct AccountRaw {
    is_duplicate: u8,
    is_signer: u8,
    is_writable: u8,
    executable: u8,
    alignment: u32,
    key: [u8; 32],
    owner: [u8; 32],
    lamports: u64,
    data_len: usize,
    data: [u8; data_len],
    padding: [u8; 10_240],
    alignment_padding: [u8; ?],
    rent_epoch: i64,
}
```
- `is_duplicate`: 목록에 동일한 계정이 두 번 이상 나타나는 경우 건너뛰어 데이터를 "재역직렬화"하지 않도록 합니다. `0xFF`는 "고유함"을 의미합니다. 다른 값은 복사할 인덱스입니다.
- `is_signer` / `is_writable` / `executable`: 프로그램이 추가 시스템 호출 없이 로직과 CPI를 제어할 수 있도록 런타임에서 사용하는 단일 바이트 플래그입니다.
- `alignment`: 전체 구조체를 8바이트 정렬로 유지하는 자리 표시자 4바이트 슬롯입니다. Pinocchio는 재할당 중에 원래 데이터 길이를 추적하기 위해 용도를 변경합니다.
- `key` / `owner` / `lamports`: 각 계정이 가져야 하는 최소한의 실행 가능한 데이터입니다.
- `data_len` + `data`: 계정에 있을 수 있는 가변 길이 데이터입니다.
- `padding`: 로더는 계정의 최대 크기인 10,240바이트를 미리 할당하므로 계정 데이터는 메모리를 이동하지 않고 제자리에서 변경되고 커질 수 있습니다.
- `align_padding`: 필요한 경우 다음 `AccountRaw`가 여전히 8바이트 경계에서 시작하도록 하는 추가 필러입니다(일부 eBPF 호스트에 중요).
- `rent_epoch`: 계정이 다음에 임대료를 지불해야 하는 에포크입니다. 임대료 징수가 일시 중지되었음에도 호환성을 위해 유지됩니다.

#### 시스템 호출 (Syscalls)

**시스템 호출** 또는 syscall은 권한이 없는 코드가 호스트의 권한 있는 서비스를 요청하는 통로입니다. syscall이 생성되면 CPU는 사용자 모드에서 신뢰할 수 있는 권한 있는 모드로 전환됩니다. 그런 다음 런타임은 요청된 작업을 수행하고 상태 코드와 함께 제어를 반환합니다. 이 간접 참조는 샌드박스 코드가 호스트 메모리나 I/O를 직접 건드리는 것을 방지하여 안전성과 결정론을 보존합니다.

Solana에서 BPF 바이트코드는 자체적으로 해시, 로그를 기록하거나 프로그램 간 호출(CPI)을 수행할 수 없습니다. 대신 `sol_log`, `sol_sha256`, `sol_invoke_signed`와 같은 명명된 시스템 호출을 호출합니다.

각 시스템 호출 번호는 단순히 로더의 디스패치 테이블에 있는 인덱스입니다. 로더는 요청된 작업을 수행하고 `u64` 상태 단어(성공 시 0, 실패 시 0이 아님)를 반환합니다.

예를 들어, `sol_invoke_signed`는 명령어, 계정 목록 및 모든 PDA 서명자 시드를 패키징하여 로더에 전달하고 로더는 다음과 같이 적절한 권한 하에 CPI를 수행합니다:

```rust
/// Solana BPF syscall for invoking a signed instruction.
fn sol_invoke_signed_c(
    instruction_addr: *const u8,
    account_infos_addr: *const u8,
    account_infos_len: u64,
    signers_seeds_addr: *const u8,
    signers_seeds_len: u64,
) -> u64;
```

<ArticleSection name="더 볼트 코드" id="the-vault-code" level="h2" />

이제 "crate 없는" Solana 프로그램의 모든 구성 요소를 풀었으므로 볼트 자체의 개요를 설명할 수 있습니다. 볼트는 정확히 두 가지 작업을 수행합니다:
- 소유자의 공개 키에서 파생된 PDA에 lamport를 **예치(Deposit)**합니다.
- 나중에 동일한 lamport를 **인출(Withdraw)**합니다. 소유자만 가능합니다.

따라서 각 명령어는 세 개의 계정을 전달합니다:
- **Owner** (서명자, 쓰기 가능): 자금을 예치하거나 인출하는 사용자입니다.
- **Vault** (쓰기 가능): 모든 lamport가 들어 있는 PDA입니다.
- **System Program**: lamport 전송을 수행하는 데 필요한 계정입니다.

시작하기 전에 새 프로젝트를 만들어야 합니다. 터미널에서 다음 명령을 실행하십시오:

```
# 작업 공간 생성
cargo new blueshift_vault --lib --edition 2021
cd blueshift_vault
```

`Cargo.toml`에 다음을 추가합니다:

```
[lib]
crate-type = ["lib", "cdylib"]
```

#### 템플릿 (Template)

모든 것은 `lib.rs`에 있을 것입니다. 한 눈에 보기에 이 파일에는 Syscall Shims(필요한 원시 syscall 레이아웃을 반영하는 작은 #[repr(C)] 구조체)와 데이터 오프셋이 상수로 포함됩니다(원시 데이터로 작업하기 쉽게 하기 위해).

#### 계정 확인 (Account Checks)

`deposit` 또는 `withdraw`를 실행하기 전에 진입점은 트랜잭션이 정확히 올바른 계정을 제공했는지, 각 계정에 예상 플래그가 있는지 확인해야 합니다.

원시 포인터 수준에서 작업하고 있기 때문에 모든 검사는 간단한 포인터 수학과 직접 로드로 수행됩니다.

입력 레코드의 처음 8바이트에는 account_len이 있습니다. 이 볼트의 경우 소유자, 볼트 PDA 및 시스템 프로그램의 세 가지 계정이 필요합니다:

```rust
// 3개의 계정이 있는지 확인: 서명자, 볼트, 프로그램
if *(input as *const u64) != 3 {
    sol_log_("Invalid number of accounts".as_ptr(), 26);
    return 1010; // NotEnoughAccountKeys Error
}
```

각 계정을 확인하는 작업을 계속합니다. 앞서 정의한 레이아웃 오프셋을 사용하면 전체 구조체를 역직렬화하지 않고도 모든 플래그를 정상성 검사할 수 있습니다.

첫 번째 계정인 서명자의 경우 수행하는 검사는 다음과 같습니다:
- 고유해야 함 (is_duplicate == 0xff)
- 쓰기 가능해야 함 (lamport를 변경할 것이므로)
- 서명자여야 함
- 실행 가능하지 않아야 함
- 데이터가 없어야 함

```rust
if *(input.add(ACCOUNT_OFFSET) as *const u32) != 0x0101ff {
    sol_log_("Invalid Account 1 Data: Non-Duplicate, Writable, Signer, Non-Executable Check Failed".as_ptr(), 58);
    return 1003; // InvalidAccountData Error
}
if *(input.add(ACCOUNT_OFFSET + DATA_LEN_OFFSET) as *const usize) != 0 {
    sol_log_("Invalid Account 1 Data: Data Length is not 0".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}
```

또한 나중에 PDA 확인을 위해 소유자의 공개 키를 보관합니다:

```rust
let signer_key = *(input.add(ACCOUNT_OFFSET + KEY_OFFSET) as *const [u8; 32]);
```

두 번째 계정인 볼트의 경우 수행하는 검사는 다음과 같습니다:
- 쓰기 가능해야 함 (lamport를 변경할 것이므로)
- 시스템 프로그램이 소유해야 함
- 데이터 길이가 0이어야 함 (여기에 상태를 저장하지 않음)

```rust
const ACCOUNT_2_OFFSET: usize = ACCOUNT_OFFSET + ACCOUNT_RAW_LEN;

if *(input.add(ACCOUNT_2_OFFSET + IS_WRITABLE_OFFSET) as *const u8) != 1 {
    sol_log_("Invalid Account 2 Data: Writable Check Failed".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}

if *(input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as *const [u8; 32]) != pinocchio_system::ID {
    sol_log_("Invalid Account 2 Data: Owner is not the System Program".as_ptr(), 48);
    return 1022; // InvalidAccountOwner Error
}

if *(input.add(ACCOUNT_2_OFFSET + DATA_LEN_OFFSET) as *const usize) != 0 {
    sol_log_("Invalid Account 2 Data: Data Length is not 0".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}
```

나중에 PDA 확인을 위해 볼트의 공개 키도 가져옵니다:

```rust
let vault_key = *(input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as *const [u8; 32]);
```

마지막 계정인 시스템 프로그램의 경우 수행하는 검사는 다음과 같습니다:
- 실행 가능해야 함
- 키가 SYSTEM_PROGRAM_ID와 같아야 함

```rust
const ACCOUNT_3_OFFSET: usize = ACCOUNT_2_OFFSET + ACCOUNT_RAW_LEN;
const SYSTEM_PROGRAM_DATA_LENGTH: usize = 14 + 2;

if *(input.add(ACCOUNT_3_OFFSET + EXECUTABLE_OFFSET) as *const u8) != 1 {
    sol_log_("Invalid Account 3 Data: Executable Check Failed".as_ptr(), 38);
    return 1003; // InvalidAccountData Error
}

if *(input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as *const [u8; 32]) != SYSTEM_PROGRAM_ID {
    sol_log_("Invalid Account 3 Data: Owner is not the System Program".as_ptr(), 48);
    return 1003; // InvalidAccountData Error
}
```

#### 명령어 확인 (Instruction checks)

계정 검증 후 마침내 명령어 페이로드를 구문 분석할 수 있습니다. 그리고 첫 번째 바이트를 구별자로 사용하여 네이티브 프로그램과 동일한 접근 방식을 취합니다:

```rust
const INSTRUCTION_OFFSET: usize = ACCOUNT_3_OFFSET + ACCOUNT_RAW_LEN + SYSTEM_PROGRAM_DATA_LENGTH + INSTRUCTION_LEN_LEN;

let discriminator = *(input.add(INSTRUCTION_OFFSET) as *const u8);
match discriminator {
    0 => {
        sol_log_("Deposit".as_ptr(), 7);

        // deposit logic …

        return 0; // Success
    }
    1 => {
        sol_log_("Withdraw".as_ptr(), 8);

        // withdraw logic …

        return 0; // Success
    }
    _ => {
        sol_log_("Invalid Instruction".as_ptr(), 20);
        return 1002; // InvalidInstructionData Error
    }
}
```

여기에서 우리는 모든 계정과 플래그가 볼트가 기대하는 것과 정확히 일치한다고 확신하면서 입금 또는 출금 핸들러로 분기합니다.

#### 입금 로직 (Deposit Logic)

입금 명령어에 대한 더 자세한 설명으로 시작하겠습니다. 모든 검사는 맨 앞에 있습니다. 통과하면 시스템 프로그램 전송을 만들고 호출합니다.

이 명령어의 명령어 데이터는 다음과 같습니다:
- 바이트 0은 구별자(입금의 경우 `0x00`)입니다.
- 바이트 1은 PDA 확인에 재사용할 범프입니다.
- 바이트 2-9는 리틀 엔디안 형식의 lamport 금액을 보유하며 0이면 거부됩니다.

```rust
let amount = *(input.add(INSTRUCTION_OFFSET + 2) as *const u64);
if amount == 0 {
    return 1002; // InvalidInstructionData Error
}
```

그 후 `sol_sha256` syscall을 사용하여 범프, 프로그램 ID 및 고유 문자열 "ProgramDerivedAddress"와 함께 소유자 키를 해시합니다.

그 결과를 계정 확인 중에 보관했던 볼트 키와 비교합니다. 다르면 `InvalidSeeds`를 반환합니다.

다르면 `InvalidSeeds`를 반환합니다.

```rust
let bump: u8 = *(input.add(INSTRUCTION_OFFSET + 1) as *const u8);
let data = [
    signer_key.as_ref(),
    &[bump],
    ID.as_ref(),
    b"ProgramDerivedAddress",
];

let mut pda = core::mem::MaybeUninit::<[u8; 32]>::uninit();
sol_sha256(
    &data as *const _ as *const u8,
    4,
    pda.as_mut_ptr(),
);

if vault_key != *pda.as_ptr() {
    sol_log_("Invalid PDA address".as_ptr(), 19);
    return 1013; // InvalidSeeds Error
};
```

마지막으로 시스템 프로그램 전송을 만들 수 있습니다.

시스템 프로그램은 4바이트 구별자(전송의 경우 해당 값은 2)를 사용하며 `from_account`에서 `to_account`로 전송하려는 금액을 나타내는 추가 8바이트가 필요합니다.

그런 다음 두 개의 SolAccountMeta 값(from = owner (서명자, 쓰기 가능), to = vault (쓰기 가능))으로 구성된 작은 배열을 빌드해야 합니다. 이를 `instruction_data`와 결합하여 `SolInstruction` 구조체를 만듭니다:

```rust
let mut instruction_data = [0; 12];
instruction_data[0] = 2; // discriminator
instruction_data[4..12].copy_from_slice(&amount.to_le_bytes()); // amount

let accounts_addr: [SolAccountMeta; 2] = [
    // from_account
    SolAccountMeta { 
        pubkey_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: true,
    },
    // to_account
    SolAccountMeta { 
        pubkey_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: false,
    },
];

// Create the instruction
let instruction = SolInstruction {
    program_id_addr: input.add(ACCOUNT_3_OFFSET + KEY_OFFSET) as u64,
    accounts_addr: accounts_addr.as_ptr() as u64,
    accounts_len: 2,
    data_addr: instruction_data.as_ptr() as u64,
    data_len: 12,
};
```

그러나 `sol_invoke_signed_c` syscall을 호출하기 전에 소유자와 볼트에 대해 각각 하나씩 두 개의 `SolAccountInfo` 구조체를 빌드해야 합니다. 이 구조체는 로더가 메모리에 남겨둔 정확한 위치에 lamport 잔액 및 데이터 슬라이스에 대한 포인터를 제공합니다.

그런 다음 명령어 포인터, 2개 요소 `SolAccountInfo` 배열에 대한 포인터 및 계정 수(2)를 전달하여 syscall을 호출할 수 있습니다. 외부 트랜잭션은 이미 소유자가 서명했으므로 여기에는 PDA 시드가 필요하지 않으므로 `signers_seeds_addr` 인수는 NULL입니다.

```rust
let account_infos_addr: [SolAccountInfo; 2] = [
    SolAccountInfo {
        is_signer: true,
        is_writable: true,
        executable: false,
        key_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        lamports_addr: input.add(ACCOUNT_OFFSET + LAMPORTS_OFFSET) as u64,
        data_len: 0,
        data_addr: input.add(ACCOUNT_OFFSET + DATA_OFFSET) as u64,
        owner_addr: input.add(ACCOUNT_OFFSET + OWNER_OFFSET) as u64,
        rent_epoch: 0,
    },
    SolAccountInfo {
        is_signer: false,
        is_writable: true,
        executable: false,
        key_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        lamports_addr: input.add(ACCOUNT_2_OFFSET + LAMPORTS_OFFSET) as u64,
        data_len: 0,
        data_addr: input.add(ACCOUNT_2_OFFSET + DATA_OFFSET) as u64,
        owner_addr: input.add(ACCOUNT_2_OFFSET + OWNER_OFFSET) as u64,
        rent_epoch: 0,
    },
];

// Invoke the instruction with the signer seeds
sol_invoke_signed_c(
    &instruction as *const SolInstruction as *const u8,
    account_infos_addr.as_ptr() as *const u8,
    2, // Number of accounts
    core::ptr::null(),
    0,
);
```

#### 출금 로직 (Withdraw Logic)

출금 명령어는 입금과 비슷하지만 몇 가지 중요한 차이점이 있습니다. 명령어 데이터가 더 간단합니다:
- 바이트 0은 구별자(출금의 경우 `0x01`)입니다.
- 바이트 1은 PDA 확인에 재사용할 범프입니다.

```rust
let bump: u8 = *(input.add(INSTRUCTION_OFFSET + 1) as *const u8);
```

소유자의 공개 키, 범프, 프로그램 ID 및 고유 문자열 "ProgramDerivedAddress"를 사용하여 입금과 동일한 PDA 확인을 수행합니다:

```rust
let data = [
    signer_key.as_ref(),
    &[bump],
    ID.as_ref(),
    b"ProgramDerivedAddress",
];

let mut pda = core::mem::MaybeUninit::<[u8; 32]>::uninit();
sol_sha256(
    &data as *const _ as *const u8,
    4,
    pda.as_mut_ptr(),
);

if vault_key != *pda.as_ptr() {
    sol_log_("Invalid PDA address".as_ptr(), 19);
    return 1013; // InvalidSeeds Error
};
```

출금의 주요 차이점은 PDA 자체로 트랜잭션에 서명해야 한다는 것입니다. 이렇게 하려면 PDA를 파생하는 데 사용된 시드를 제공해야 합니다. 두 개의 요소가 있는 `SolSignerSeedsC` 배열을 만듭니다:
- 소유자의 공개 키 (32바이트)
- 범프 (1바이트)

```rust
let seeds: [SolSignerSeedsC; 2] = [
    SolSignerSeedsC {
        addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        len: 32,
    },
    SolSignerSeedsC {
        addr: input.add(INSTRUCTION_OFFSET + 1) as u64,
        len: 1,
    },
];

let signer_seeds_addr: [SolSignerSeedsC; 1] = [
    SolSignerSeedsC {
        addr: seeds.as_ptr() as u64,
        len: 2,
    },
];
```

그런 다음 시스템 프로그램 전송 명령어를 만들지만 이번에는 볼트에서 소유자에게로 전송합니다. 명령어 데이터는 입금과 동일합니다:
- 4바이트 구별자 (전송의 경우 값 2)
- 금액에 대한 8바이트 (볼트의 lamport에서 가져옴)

```rust
let amount = *(input.add(ACCOUNT_2_OFFSET + LAMPORTS_OFFSET) as *const u64);

let mut instruction_data = [0; 12];
instruction_data[0] = 2;
instruction_data[4..12].copy_from_slice(&amount.to_le_bytes());
```

계정 메타는 입금에 비해 역전됩니다:
- 첫 번째 계정은 볼트 (쓰기 가능, 서명자)
- 두 번째 계정은 소유자 (쓰기 가능)

```rust
let account_addr: [SolAccountMeta; 2] = [
    SolAccountMeta {
        pubkey_addr: input.add(ACCOUNT_2_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: true,
    },
    SolAccountMeta {
        pubkey_addr: input.add(ACCOUNT_OFFSET + KEY_OFFSET) as u64,
        is_writable: true,
        is_signer: false,
    },
];
```

마지막으로 명령어, 계정 정보 및 앞서 만든 서명자 시드를 사용하여 `sol_invoke_signed_c`를 호출합니다:

```rust
sol_invoke_signed_c(
    &instruction as *const SolInstruction as *const u8,
    account_infos_addr.as_ptr() as *const u8,
    2, // Number of accounts
    signer_seeds_addr.as_ptr() as *const u8,
    1,
);
```

<ArticleSection name="맺음말" id="closing-remarks" level="h2" />

Solana 프로그램을 작성하는 이 로우 레벨 접근 방식이 극단적으로 보일 수 있지만 중요한 교육적 목적을 제공합니다. 우리는 이런 식으로 프로그램을 작성하라고 제안하는 것이 아닙니다. 사실, 이러한 복잡성을 추상화하는 확립된 프레임워크와 crate를 사용하는 것을 강력히 권장합니다. 그러나 기본 역학을 이해하는 것은 매우 중요합니다.

`solana_program`, `anchor` 또는 기타 프레임워크 등 Solana 개발에서 사용하는 모든 추상화는 이러한 기본 구성 요소 위에 구축됩니다. 레이어를 벗겨내고 원시 역학을 검토함으로써 다음에 대한 더 깊은 이해를 얻을 수 있습니다:

1. Solana 런타임이 프로그램과 상호 작용하는 방식
2. 상위 수준 프레임워크에서 특정 설계 결정이 내려진 이유
3. 잠재적인 최적화가 존재할 수 있는 곳
4. 문제가 발생했을 때 더 잘 디버깅하는 방법

이 지식은 단지 학문적인 것이 아니라 실용적입니다. 기초를 이해하면 다음을 수행할 수 있습니다:
- 데이터 구조 및 메모리 사용에 대한 정보에 입각한 결정을 내려 더 효율적인 프로그램을 작성합니다.
- 문제가 발생할 때 더 잘 진단하고 수정합니다.
- 우리 모두가 사용하는 도구를 개선하여 생태계에 기여합니다.
- 특정 추상화를 사용할 때와 금속에 더 가깝게 작업할 때에 대해 정보에 입각한 결정을 내립니다.

이 연습의 목표는 crate 없이 프로그램을 작성하는 방법을 가르치는 것이 아니라 해당 crate가 내부적으로 수행하는 작업을 이해하도록 돕는 것입니다. 이러한 이해는 사용하기로 선택한 도구에 관계없이 더 좋고 효율적인 Solana 프로그램을 작성하기 위한 첫 번째 단계입니다.
