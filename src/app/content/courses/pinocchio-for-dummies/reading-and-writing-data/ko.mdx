# 데이터 읽고 쓰기 (Reading and Writing Data)

최적화된 Solana 프로그램을 구축할 때 효율적인 데이터 직렬화 및 역직렬화는 성능에 상당한 영향을 미칠 수 있습니다.

Pinocchio는 저수준 메모리 작업을 필요로 하지 않지만, 계정 데이터를 효율적으로 읽고 쓰는 방법을 이해하면 더 빠른 프로그램을 구축하는 데 도움이 될 수 있습니다.

이 가이드의 기술은 Pinocchio, Anchor 또는 네이티브 SDK를 사용하든 모든 Solana 개발 프레임워크와 함께 작동합니다. 핵심은 데이터 구조를 신중하게 설계하고 직렬화를 안전하게 처리하는 것입니다.

### 안전하지 않은 코드를 사용해야 할 때 (When to Use Unsafe Code)

다음 경우에만 안전하지 않은(unsafe) 코드를 사용하십시오:
- 최대 성능이 필요하고 안전한 대안이 너무 느리다는 것을 측정한 경우
- 모든 안전 불변성을 엄격하게 확인할 수 있는 경우
- 안전 요구 사항을 명확하게 문서화한 경우

> 가능하면 안전한 대안을 선호하십시오.

<ArticleSection name="안전 원칙" id="safety-principles" level="h2" />

원시 바이트 배열 및 메모리 작업으로 작업할 때는 정의되지 않은 동작을 피하도록 주의해야 합니다. 이러한 원칙을 이해하는 것은 정확하고 신뢰할 수 있는 코드를 작성하는 데 중요합니다.

### 버퍼 경계 확인 (Buffer Bounds Checking)

읽기 또는 쓰기 작업 전에 버퍼가 충분히 큰지 항상 확인하십시오. 할당된 메모리를 넘어 읽거나 쓰는 것은 정의되지 않은 동작입니다.

```rust
// 좋음: 경계 먼저 확인
if data.len() < size_of::<u64>() {
    return Err(ProgramError::InvalidInstructionData);
}
let value = u64::from_le_bytes(data[0..8].try_into().unwrap());

// 나쁨: 경계 확인 없음 - 패닉이 발생하거나 UB를 유발할 수 있음
let value = u64::from_le_bytes(data[0..8].try_into().unwrap());
```

### 정렬 요구 사항 (Alignment Requirements)

Rust의 모든 유형에는 메모리에 배치할 수 있는 위치를 결정하는 정렬 요구 사항이 있습니다. 제대로 정렬되지 않은 메모리에서 유형을 읽으면 정의되지 않은 동작이 발생합니다. 대부분의 기본 유형은 크기와 동일한 정렬이 필요합니다:
- `u8`: 1바이트 정렬
- `u16`: 2바이트 정렬
- `u32`: 4바이트 정렬
- `u64`: 8바이트 정렬

즉, `u64`는 8로 나누어 떨어지는 메모리 주소에 저장되어야 하며 `u16`은 짝수 주소에서 시작해야 합니다.

이것이 준수되지 않으면 컴파일러는 각 필드가 정렬 요구 사항을 충족하도록 구조체 필드 사이에 보이지 않는 "패딩" 바이트를 자동으로 삽입합니다.

> 또한 구조체의 전체 크기는 가장 큰 필드의 정렬 요구 사항의 배수여야 합니다.

잘못 정렬된 구조체는 다음과 같습니다:

```rust
#[repr(C)]
struct BadOrder {
    small: u8,    // 1바이트
    // `big`이 8바이트 정렬되어야 하므로 여기에 패딩: [u8; 7]
    big: u64,     // 8바이트
    medium: u16,  // 2바이트
    // 구조체 크기가 8바이트 정렬되어야 하므로 여기에 패딩: [u8; 6]
}
```

컴파일러는 `big`이 8바이트 정렬을 필요로 하기 때문에 `small` 뒤에 7개의 패딩 바이트를 삽입합니다. 그런 다음 전체 크기(24바이트)를 8의 배수로 만들기 위해 끝에 6개의 바이트를 더 추가하여 13바이트를 낭비합니다.

더 좋은 방법은 다음과 같이 구조체의 필드를 정렬하는 것입니다:

```rust
#[repr(C)]
struct GoodOrder {
    big: u64,     // 8바이트
    medium: u16,  // 2바이트
    small: u8,    // 1바이트
    // 구조체 크기가 8바이트 정렬되어야 하므로 여기에 패딩: [u8; 5]
}
```

더 큰 필드를 먼저 배치함으로써 패딩을 13바이트에서 5바이트로 줄입니다.

> 황금률은 패딩을 최소화하고 메모리 사용량을 줄이기 위해 구조체 필드를 정렬 요구 사항이 가장 큰 것부터 가장 작은 것 순서로 정렬하는 것입니다.

공간 효율성을 극대화하기 위해 데이터를 직렬화하고 역직렬화하는 또 다른 고급 방법이 있습니다. 정렬 요구 사항이 완전히 제거된 제로 패딩 구조체(Zero-Padding Structs)를 만들 수 있습니다:

```rust
#[repr(C)]
struct ByteArrayStruct {
    big: [u8; 8],    // u64를 나타냄
    medium: [u8; 2], // u16을 나타냄
    small: u8,
}
```

이 경우 모든 것이 1바이트 정렬되므로 크기는 정확히 11바이트입니다.

### 유효한 비트 패턴 (Valid Bit Patterns)

모든 비트 패턴이 모든 유형에 유효한 것은 아닙니다. `bool`, `char`, `enums`와 같은 유형에는 제한된 유효 값이 있습니다. 이러한 유형으로 잘못된 비트 패턴을 읽는 것은 정의되지 않은 동작입니다.

<ArticleSection name="데이터 읽기" id="reading-data" level="h2" />

계정 버퍼에서 데이터를 읽는 방법에는 몇 가지가 있으며 각각 장단점이 있습니다:

### 필드별 역직렬화 (Field-by-Field Deserialization) (권장)

가장 안전한 접근 방식은 각 필드를 개별적으로 역직렬화하는 것입니다. 바이트 배열로 작업하기 때문에 모든 정렬 문제를 피할 수 있습니다:

```rust
pub struct DepositInstructionData {
    pub amount: u64,
    pub recipient: Pubkey,
}

impl<'a> TryFrom<&'a [u8]> for DepositInstructionData {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        if data.len() < (size_of::<u64>() + size_of::<Pubkey>()) {
            return Err(ProgramError::InvalidInstructionData);
        }

        // 정렬 문제 없음: 바이트를 읽고 변환
        let amount = u64::from_le_bytes(
            data[0..8].try_into()
                .map_err(|_| ProgramError::InvalidInstructionData)?
        );
        
        let recipient = Pubkey::try_from(&data[8..40])
            .map_err(|_| ProgramError::InvalidInstructionData)?;

        Ok(Self { amount, recipient })
    }
}
```

### 제로 카피 역직렬화 (Zero-Copy Deserialization)

적절하게 정렬된 구조체로 최대 성능을 위해 사용할 수 있지만 신중한 정렬 확인이 필요합니다:

```rust
#[repr(C)]
pub struct Config {
    pub authority: Pubkey,
    pub mint_x: Pubkey, 
    pub mint_y: Pubkey,
    pub seed: u64,        // 이 필드는 8바이트 정렬이 필요합니다
    pub fee: u16,         // 이 필드는 2바이트 정렬이 필요합니다
    pub state: u8,
    pub config_bump: u8,
}

impl Config {
    pub const LEN: usize = size_of::<Self>();
    
    pub fn from_bytes(data: &[u8]) -> Result<&Self, ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }

        // 중요: 가장 제한적인 필드(이 경우 u64)에 대한 정렬 확인
        if (data.as_ptr() as usize) % core::mem::align_of::<Self>() != 0 {
            return Err(ProgramError::InvalidAccountData);
        }

        // 안전: 길이와 정렬을 확인했습니다
        Ok(unsafe { &*(data.as_ptr() as *const Self) })
    }
}

// 대안: 정렬 요구 사항이 1보다 큰 유형에 대해 바이트 배열을 사용하고 접근자 메서드를 제공하여 정렬 문제를 완전히 방지합니다
#[repr(C)]
pub struct ConfigSafe {
    pub authority: Pubkey,
    pub mint_x: Pubkey, 
    pub mint_y: Pubkey,
    seed: [u8; 8],      // 필요할 때 u64::from_le_bytes로 변환
    fee: [u8; 2],       // 필요할 때 u16::from_le_bytes로 변환
    pub state: u8,
    pub config_bump: u8,
}

impl ConfigSafe {
    pub fn from_bytes(data: &[u8]) -> Result<&Self, ProgramError> {
        if data.len() != size_of::<Self>() {
            return Err(ProgramError::InvalidAccountData);
        }

        // 안전: 정렬 확인 필요 없음 - 모든 것이 u8 정렬됨
        Ok(unsafe { &*(data.as_ptr() as *const Self) })
    }
    
    pub fn seed(&self) -> u64 {
        u64::from_le_bytes(self.seed)
    }
    
    pub fn fee(&self) -> u16 {
        u16::from_le_bytes(self.fee)
    }
}
```

보시다시피 seed와 fee 필드는 모두 비공개입니다. 해당 값은 바이트 배열로 표현되므로 데이터를 읽으려면 항상 접근자 메서드를 사용해야 하기 때문입니다.

필드에 직접 액세스할 때(`config.seed`), 컴파일러는 일시적으로라도 해당 필드의 메모리 위치에 대한 참조를 생성해야 할 수 있습니다. 해당 필드가 제대로 정렬되지 않은 경우 해당 참조를 생성하는 것은 참조를 명시적으로 사용하지 않더라도 정의되지 않은 동작입니다!

접근자 메서드는 컴파일러가 중간 참조를 최적화할 수 있는 메서드 범위 내에서 읽기 작업을 수행하여 이를 방지합니다.

```rust
#[repr(C, packed)]  // 이로 인해 정렬되지 않은 필드가 발생할 수 있습니다!
pub struct PackedConfig {
    pub state: u8,
    pub seed: u64,    // 이 u64는 패킹으로 인해 8바이트 정렬되지 않을 수 있습니다
}

impl PackedConfig {
    pub fn seed(&self) -> u64 {
        self.seed  // 안전: 직접 값 복사, 참조 생성 안 됨
    }
}

// 사용법:
let config = PackedConfig::load(account)?;

// ❌ 정의되지 않은 동작: 잠재적으로 정렬되지 않은 필드에 대한 참조 생성
let seed_ref = &config.seed; // 컴파일러는 여기서 참조를 생성해야 합니다!

// ❌ 정의되지 않은 동작: 이것조차도 문제가 될 수 있습니다
let seed_value = config.seed; // 내부적으로 임시 참조를 생성할 수 있음

// ✅ 안전: 접근자 메서드는 참조를 생성하지 않고 값을 읽습니다
let seed_value = config.seed(); // 중간 참조 없음
```

> `u8` 필드는 항상 1의 정렬을 가지며 항상 정렬되므로 `self.state`를 직접 사용할 수 있어 직접 액세스하는 것이 안전합니다.

이 경우 "특수 유형"이 없지만 잘못된 비트 패턴으로 인해 일부 유형에는 특별한 주의가 필요하다는 점을 항상 기억하십시오:

```rust
pub struct StateAccount {
    pub is_active: bool,
    pub state_type: StateType,
    pub data: [u8; 32],
}

#[repr(u8)]
pub enum StateType {
    Inactive = 0,
    Active = 1,
    Paused = 2,
}

impl StateAccount {
    pub fn from_bytes(data: &[u8]) -> Result<Self, ProgramError> {
        if data.len() < size_of::<Self>() {
            return Err(ProgramError::InvalidAccountData);
        }

        // bool을 안전하게 처리 (0 또는 1만 유효함)
        let is_active = match data[0] {
            0 => false,
            1 => true,
            _ => return Err(ProgramError::InvalidAccountData),
        };

        // enum을 안전하게 처리
        let state_type = match data[1] {
            0 => StateType::Inactive,
            1 => StateType::Active, 
            2 => StateType::Paused,
            _ => return Err(ProgramError::InvalidAccountData),
        };

        let mut data_array = [0u8; 32];
        data_array.copy_from_slice(&data[2..34]);

        Ok(Self {
            is_active,
            state_type,
            data: data_array,
        })
    }
}
```

### 피해야 할 위험한 패턴

다음은 정의되지 않은 동작으로 이어질 수 있으며 피해야 할 일반적인 패턴입니다:

1. 정렬되지 않은 데이터에 `transmute()` 사용

```rust
// ❌ 정의되지 않은 동작: transmute는 적절한 정렬이 필요합니다
let value: u64 = unsafe { core::mem::transmute(bytes_slice) };
```

`transmute()`는 소스 데이터가 대상 유형에 대해 적절하게 정렬되어 있다고 가정합니다. 임의의 바이트 슬라이스로 작업하는 경우 이 가정이 위반되는 경우가 많습니다.

2. 패킹된 구조체에 대한 포인터 캐스팅

```rust
#[repr(C, packed)]
pub struct PackedConfig {
    pub state: u8,
    pub seed: u64,     // 이 u64는 1바이트 정렬만 됩니다!
    pub authority: Pubkey,
}

// ❌ 정의되지 않은 동작: 정렬되지 않은 필드에 대한 참조 생성
let config = unsafe { &*(data.as_ptr() as *const PackedConfig) };
let seed_value = config.seed; // UB: 정렬되지 않은 u64에 대한 참조를 생성할 수 있음
```

구조체가 메모리에 맞더라도 멀티바이트 필드에 액세스하면 정렬되지 않은 참조가 생성될 수 있습니다.

3. 패킹된 구조체의 직접 필드 액세스

```rust
#[repr(C, packed)]
pub struct PackedStruct {
    pub a: u8,
    pub b: u64,
}

let packed = /* ... */;
// ❌ 정의되지 않은 동작: 정렬되지 않은 필드에 대한 참조 생성
let b_ref = &packed.b;
// ❌ 정의되지 않은 동작: 임시 참조를 생성할 수 있음
let b_value = packed.b;
```

4. 검증 없이 정렬 가정

```rust
// ❌ 정의되지 않은 동작: 정렬 확인 없음
let config = unsafe { &*(data.as_ptr() as *const Config) };
```

데이터가 맞는다고 해서 제대로 정렬된 것은 아닙니다.

5. `read_unaligned()`를 잘못 사용

```rust
// ❌ 잘못됨: read_unaligned는 크기뿐만 아니라 적절한 레이아웃이 필요합니다
#[repr(Rust)]  // 기본 레이아웃 - 보장되지 않음!
pub struct BadStruct {
    pub field: u64,
}

let value = unsafe { (data.as_ptr() as *const BadStruct).read_unaligned() };
```

`read_unaligned()`는 여전히 구조체가 예측 가능한 레이아웃(`#[repr(C)]`)을 가져야 합니다.

<ArticleSection name="데이터 쓰기" id="writing-data" level="h2" />

데이터를 안전하게 쓰는 것은 읽기와 유사한 원칙을 따릅니다:

### 필드별 직렬화 (Recommended)

```rust
impl Config {
    pub fn write_to_buffer(&self, data: &mut [u8]) -> Result<(), ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }

        let mut offset = 0;
        
        // Write authority
        data[offset..offset + 32].copy_from_slice(self.authority.as_ref());
        offset += 32;
        
        // Write mint_x  
        data[offset..offset + 32].copy_from_slice(self.mint_x.as_ref());
        offset += 32;
        
        // Write mint_y
        data[offset..offset + 32].copy_from_slice(self.mint_y.as_ref());
        offset += 32;
        
        // Write seed
        data[offset..offset + 8].copy_from_slice(&self.seed.to_le_bytes());
        offset += 8;
        
        // Write fee
        data[offset..offset + 2].copy_from_slice(&self.fee.to_le_bytes());
        offset += 2;
        
        // Write state
        data[offset] = self.state;
        offset += 1;
        
        // Write config_bump
        data[offset] = self.config_bump;

        Ok(())
    }
}
```

이 접근 방식은 각 필드를 바이트 버퍼에 명시적으로 직렬화하기 때문에 가장 안전한 방법입니다:
- 정렬 문제 없음: 바이트 배열에 씀
- 명시적 엔디안: to_le_bytes()로 바이트 순서 제어
- 명확한 메모리 레이아웃: 디버그 및 이해하기 쉬움
- 정의되지 않은 동작 없음: 모든 작업은 바이트 배열에서 수행됨

### 직접 변형 (제로 카피)

최대 성능을 위해 바이트 버퍼를 구조체로 캐스팅하고 필드를 직접 변경할 수 있습니다. 이를 위해서는 구조체가 적절하게 정렬되어야 합니다:

```rust
impl Config {
    pub fn from_bytes_mut(data: &mut [u8]) -> Result<&mut Self, ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }

        // 정렬 확인
        if (data.as_ptr() as usize) % core::mem::align_of::<Self>() != 0 {
            return Err(ProgramError::InvalidAccountData);
        }

        // 안전: 길이와 정렬을 확인했습니다
        Ok(unsafe { &mut *(data.as_mut_ptr() as *mut Self) })
    }
}
```

정렬이 확인되고 구조체에 `#[repr(C)]`가 사용되면 직접적인 필드 변형은 정렬되지 않은 참조를 생성하지 않습니다.

### 설정자가 있는 바이트 배열 접근 방식 (가장 안전함 + 빠름)

두 세계의 장점: 내부적으로 바이트 배열을 사용하지만 인체 공학적인 설정자를 제공할 수 있습니다:

```rust
#[repr(C)]
pub struct ConfigSafe {
    pub authority: Pubkey,
    pub mint_x: Pubkey, 
    pub mint_y: Pubkey,
    seed: [u8; 8],
    fee: [u8; 2],
    pub state: u8,
    pub config_bump: u8,
}

impl ConfigSafe {
    pub fn from_bytes_mut(data: &mut [u8]) -> Result<&mut Self, ProgramError> {
        if data.len() != size_of::<Self>() {
            return Err(ProgramError::InvalidAccountData);
        }

        // 정렬 확인 필요 없음 - 모든 것이 u8 정렬됨
        Ok(unsafe { &mut *(data.as_mut_ptr() as *mut Self) })
    }
    
    pub fn seed(&self) -> u64 {
        u64::from_le_bytes(self.seed)
    }
    
    pub fn fee(&self) -> u16 {
        u16::from_le_bytes(self.fee)
    }

    // 엔디안을 올바르게 처리하는 설정자

    pub fn set_seed(&mut self, seed: u64) {
        self.seed = seed.to_le_bytes();
    }
    
    pub fn set_fee(&mut self, fee: u16) {
        self.fee = fee.to_le_bytes();
    }
}
```

이것이 이상적인 이유는 다음과 같습니다:
- 정렬 문제 없음: 모든 필드는 바이트 정렬됨
- 빠른 직접 변형: 초기 설정 후 직렬화 오버헤드 없음
- 일관된 엔디안: 설정자는 바이트 순서 변환을 처리함
- 타입 안전성: 설정자는 바이트 배열이 아닌 예상 유형을 사용함

<ArticleSection name="동적으로 크기가 조정되는 데이터" id="dynamically-sized-data" level="h2" />

가능하면 계정에 동적으로 크기가 조정되는 데이터를 직접 저장하지 마십시오. 그러나 일부 사용 사례에서는 필요합니다.

계정에 동적 데이터가 포함된 경우 모든 정적 크기 필드를 구조체의 시작 부분에 배치하고 동적 데이터를 끝에 추가하십시오.

### 단일 동적 필드 (Single Dynamic Field)

이것은 가장 간단한 경우입니다. 계정 끝에 하나의 가변 길이 섹션이 있습니다:

```rust
#[repr(C)]
pub struct DynamicAccount {
    pub fixed_data: [u8; 32],
    pub counter: u64,
    // 동적 데이터는 메모리에서 구조체 뒤에 따릅니다
    // 레이아웃: [fixed_data][counter][dynamic_data...]
}

impl DynamicAccount {
    pub const FIXED_SIZE: usize = size_of::<Self>();
    
    /// 동적 데이터로 계정 안전하게 파싱
    pub fn from_bytes_with_dynamic(data: &[u8]) -> Result<(&Self, &[u8]), ProgramError> {
        if data.len() < Self::FIXED_SIZE {
            return Err(ProgramError::InvalidAccountData);
        }

        // 안전: 버퍼가 고정 부분에 대해 충분히 큰지 확인했습니다
        // 고정 부분에는 [u8; 32] 및 u64만 포함되며 레이아웃이 예측 가능합니다
        let fixed_part = unsafe { &*(data.as_ptr() as *const Self) };
        
        // 고정 부분 이후의 모든 것은 동적 데이터입니다
        let dynamic_part = &data[Self::FIXED_SIZE..];
        
        Ok((fixed_part, dynamic_part))
    }
    
    /// 두 부분에 대한 가변 참조 가져오기
    pub fn from_bytes_mut_with_dynamic(data: &mut [u8]) -> Result<(&mut Self, &mut [u8]), ProgramError> {
        if data.len() < Self::FIXED_SIZE {
            return Err(ProgramError::InvalidAccountData);
        }

        // 차용 문제를 피하기 위해 버퍼 분할
        let (fixed_bytes, dynamic_bytes) = data.split_at_mut(Self::FIXED_SIZE);
        
        // 안전: 크기를 확인하고 안전하게 분할했습니다
        let fixed_part = unsafe { &mut *(fixed_bytes.as_mut_ptr() as *mut Self) };
        
        Ok((fixed_part, dynamic_bytes))
    }
}

/// 단일 동적 필드 쓰기
impl DynamicAccount {
    pub fn write_with_dynamic(
        data: &mut [u8], 
        fixed_data: &[u8; 32], 
        counter: u64,
        dynamic_data: &[u8]
    ) -> Result<(), ProgramError> {
        let total_size = Self::FIXED_SIZE + dynamic_data.len();
        
        if data.len() != total_size {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // 고정 부분을 필드별로 쓰기 (가장 안전한 접근 방식)
        data[0..32].copy_from_slice(fixed_data);
        data[32..40].copy_from_slice(&counter.to_le_bytes());
        
        // 동적 부분 쓰기
        data[Self::FIXED_SIZE..].copy_from_slice(dynamic_data);
        
        Ok(())
    }
    
    /// 동적 부분만 업데이트
    pub fn update_dynamic_data(&mut self, account_data: &mut [u8], new_data: &[u8]) -> Result<(), ProgramError> {
        if account_data.len() < Self::FIXED_SIZE + new_data.len() {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // 새로운 동적 데이터 쓰기
        account_data[Self::FIXED_SIZE..Self::FIXED_SIZE + new_data.len()].copy_from_slice(new_data);
        
        Ok(())
    }
}
```

정의되지 않은 동작을 방지하려면 계정 데이터 버퍼가 젂어도 정적 크기 부분만큼 큰지 항상 확인하십시오. 동적 섹션은 비어 있을 수 있으므로 이 검사는 필수적입니다.

이 레이아웃은 동적 데이터의 길이에 관계없이 고정 크기 필드의 오프셋이 항상 알려지도록 합니다.

동적으로 크기가 조정되는 데이터를 읽을 때 두 가지 주요 시나리오가 있습니다:

- 끝에 단일 동적 필드: 런타임에 동적 데이터의 크기와 오프셋을 쉽게 결정할 수 있습니다:

```rust
const DYNAMIC_DATA_START_OFFSET: usize = size_of::<[u8; 32]>();

#[repr(C)]
pub struct DynamicallySizedAccount {
    pub sized_data: [u8; 32],
    // pub dynamic_data: &'info [u8], // 구조체의 일부가 아니지만 버퍼에서 뒤따릅니다
}

impl DynamicallySizedAccount {
    /// 동적 데이터 섹션의 길이를 반환합니다.
    #[inline(always)]
    pub fn get_dynamic_data_len(data: &[u8]) -> Result<usize, ProgramError> {
        if data.len().le(&DYNAMIC_DATA_START_OFFSET) {
            return Err(ProgramError::InvalidAccountData);
        }

        Ok(data.len() - DYNAMIC_DATA_START_OFFSET)
    }

    /// 동적 데이터의 슬라이스를 반환합니다.
    #[inline(always)]
    pub fn read_dynamic_data(data: &[u8]) -> Result<&[u8], ProgramError> {
        if data.len().le(&DYNAMIC_DATA_START_OFFSET) {
            return Err(ProgramError::InvalidAccountData);
        }

        Ok(&data[DYNAMIC_DATA_START_OFFSET..])
    }
}
```

### 다중 동적 필드 (Multiple Dynamic Fields)

이 접근 방식은 마지막을 제외한 각 동적 필드의 길이를 결정하는 방법이 필요하므로 더 복잡합니다. 가장 일반적인 방법은 버퍼를 올바르게 구문 분석할 수 있도록 각 동적 필드(마지막 제외) 앞에 길이를 접두사로 붙이는 것입니다.

간단하고 강력한 패턴은 다음과 같습니다: 정적 크기 데이터 바로 뒤에 `u8`(또는 더 큰 크기가 필요한 경우 `u16` 등)로 첫 번째 동적 필드의 길이를 저장합니다. 첫 번째 동적 필드가 뒤따르고 두 번째 동적 필드가 버퍼의 나머지 부분 차지합니다.

```rust
#[repr(C)]  
pub struct MultiDynamicAccount {
    pub fixed_data: [u8; 32],
    pub timestamp: u64,
    // 레이아웃: [fixed_data][timestamp][len1: u8][data1][data2: 나머지]
}

impl MultiDynamicAccount {
    pub const FIXED_SIZE: usize = size_of::<Self>();
    pub const LEN_PREFIX_SIZE: usize = size_of::<u8>();
    pub const MIN_SIZE: usize = Self::FIXED_SIZE + Self::LEN_PREFIX_SIZE;
    
    /// 두 개의 동적 섹션으로 계정 구문 분석
    pub fn parse_dynamic_fields(data: &[u8]) -> Result<(&[u8; 32], u64, &[u8], &[u8]), ProgramError> {
        if data.len() < Self::MIN_SIZE {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // 고정 데이터 안전하게 추출
        let fixed_data = data[..32].try_into()
            .map_err(|_| ProgramError::InvalidAccountData)?;
            
        let timestamp = u64::from_le_bytes(
            data[32..40].try_into()
                .map_err(|_| ProgramError::InvalidAccountData)?
        );
            
        // 첫 번째 동적 필드의 길이 읽기 (단일 바이트)
        let len = data[Self::FIXED_SIZE] as usize;
        
        // 충분한 데이터가 있는지 확인
        if data.len() <  Self::MIN_SIZE + len {
            return Err(ProgramError::InvalidAccountData);
        }
        
        let data_1 = &data[Self::MIN_SIZE..Self::MIN_SIZE + len];
        let data_2 = &data[Self::MIN_SIZE + len..]; // 나머지
        
        Ok((fixed_data, timestamp, data_1, data_2))
    }
    
    /// 두 개의 동적 섹션으로 계정 쓰기
    pub fn write_with_multiple_dynamic(
        buffer: &mut [u8],
        fixed_data: &[u8; 32],
        timestamp: u64,
        data_1: &[u8],
        data_2: &[u8]
    ) -> Result<(), ProgramError> {
        let total_size = Self::MIN_SIZE + data_1.len() + data_2.len();
        
        if buffer.len() != total_size {
            return Err(ProgramError::InvalidAccountData);
        }
        
        // data_1 길이가 u8에 맞는지 확인
        if data_1.len() > u8::MAX as usize {
            return Err(ProgramError::InvalidInstructionData);
        }
        
        let mut offset = 0;
        
        // 고정 데이터 쓰기
        buffer[offset..offset + 32].copy_from_slice(fixed_data);
        offset += 32;
        
        buffer[offset..offset + 8].copy_from_slice(&timestamp.to_le_bytes());
        offset += 8;
        
        // data1에 대한 길이 접두사 쓰기 (단일 바이트)
        buffer[offset] = data_1.len() as u8;
        offset += 1;
        
        // data1 쓰기
        buffer[offset..offset + data_1.len()].copy_from_slice(data_1);
        offset += data_1.len();
        
        // data2 쓰기 (나머지 - 길이 접두사 필요 없음)
        buffer[offset..].copy_from_slice(data_2);
        
        Ok(())
    }
}
```

### 계정 크기 조정 (Resize the account)

동적 필드를 업데이트할 때마다 크기가 변경되면 계정 크기를 조정해야 합니다. 다음은 계정 크기 조정을 위한 범용 함수입니다:

```rust
pub fn resize_account(
    account: &AccountInfo,
    payer: &AccountInfo,
    new_size: usize,
    zero_out: bool,
) -> ProgramResult {
    // 계정 크기가 이미 정확하다면 일찍 반환
    if new_size == account.data_len() {
        return Ok(());
    }

    // 임대료 요구 사항 계산
    let rent = Rent::get()?;
    let new_minimum_balance = rent.minimum_balance(new_size);

    // 임대료 면제 요구 사항을 충족하도록 lamport 조정
    match new_minimum_balance.cmp(&account.lamports()) {
        core::cmp::Ordering::Greater => {
            // 임대료 면제를 위해 더 많은 lamport 필요
            let lamports_diff = new_minimum_balance.saturating_sub(account.lamports());
            **payer.try_borrow_mut_lamports()? -= lamports_diff;
            **account.try_borrow_mut_lamports()? += lamports_diff;
        }
        core::cmp::Ordering::Less => {
            // 초과 lamport를 지불자에게 반환
            let lamports_diff = account.lamports().saturating_sub(new_minimum_balance);
            **account.try_borrow_mut_lamports()? -= lamports_diff;
            **payer.try_borrow_mut_lamports()? += lamports_diff;
        }
        core::cmp::Ordering::Equal => {
            // lamport 전송 필요 없음
        }
    }

    // 계정 재할당
    account.resize(new_size)?;

    Ok(())
}
```
