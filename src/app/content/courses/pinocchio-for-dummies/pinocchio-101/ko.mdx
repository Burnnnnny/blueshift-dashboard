# 피노키오 101 (Pinocchio 101)

![Introduction to Pinocchio](/graphics/course-banners/introduction-to-pinocchio.png)

<ArticleSection name="피노키오란 무엇인가?" id="what-is-pinocchio" level="h2" />

대부분의 Solana 개발자가 Anchor에 의존하지만, Anchor 없이 프로그램을 작성해야 할 좋은 이유도 많이 있습니다. 모든 계정 필드에 대한 세밀한 제어가 필요하거나, 최대 성능을 추구하거나, 단순히 매크로를 피하고 싶을 수도 있습니다.

Anchor와 같은 프레임워크 없이 Solana 프로그램을 작성하는 것을 **네이티브 개발(Native development)**이라고 합니다. 이는 더 까다롭지만, 이 코스에서는 Pinocchio를 사용하여 처음부터 Solana 프로그램을 만드는 법을 배웁니다. Pinocchio는 외부 프레임워크를 건너뛰고 코드의 모든 바이트를 소유할 수 있게 해주는 경량 라이브러리입니다.

Pinocchio는 무거운 `solana-program` 크레이트를 가져오지 않고도 Solana 프로그램을 만들 수 있게 해주는 미니멀한 Rust 라이브러리입니다. 들어오는 트랜잭션 페이로드(계정, 명령어 데이터 등 모든 것)를 단일 바이트 슬라이스로 처리하고 제로 카피(zero-copy) 기술을 통해 제자리에서 읽습니다.

### 주요 장점 (Key advantages)

미니멀한 디자인은 세 가지 큰 이점을 제공합니다:
- 더 적은 컴퓨팅 유닛 (Compute units). 추가적인 역직렬화나 메모리 복사가 없습니다.
- 더 작은 바이너리. 더 간결한 코드 경로는 온체인에서 더 가벼운 `.so`를 의미합니다.
- 제로 의존성 부담. 업데이트(하거나 깨질) 외부 크레이트가 없습니다.

이 프로젝트는 [Anza](https://www.anza.xyz)의 [Febo](https://x.com/0x_febo)가 시작했으며, Solana 생태계와 Blueshift 팀의 핵심 기여로 [여기](https://github.com/anza-xyz/pinocchio)에 있습니다.

핵심 크레이트와 함께 `pinocchio-system` 및 `pinocchio-token`을 찾을 수 있는데, 이는 Solana의 네이티브 시스템 및 SPL 토큰 프로그램을 위한 제로 카피 헬퍼 및 CPI 유틸리티를 제공합니다.

### 네이티브 개발 (Native Development)

네이티브 개발이 벅차게 들릴 수도 있지만, 이것이 바로 이 챕터가 존재하는 이유입니다. 끝날 때쯤이면 프로그램 경계를 넘는 모든 바이트와 로직을 촘촘하고 안전하며 빠르게 유지하는 방법을 이해하게 될 것입니다.

Anchor는 **절차적 및 파생 매크로(Procedural and Derive Macros)**를 사용하여 Solana 프로그램 구축의 핵심인 계정, 명령어 데이터 및 오류 처리를 다루는 상용구를 단순화합니다.

네이티브로 간다는 것은 더 이상 그러한 사치를 누릴 수 없으며 다음을 수행해야 함을 의미합니다:
- 다른 명령어에 대한 자체 구별자(Discriminator) 및 진입점(Entrypoint) 생성
- 자체 계정, 명령어 및 역직렬화 로직 생성
- 이전에 Anchor가 우리를 위해 수행하던 모든 보안 검사 구현

**참고**: Pinocchio 프로그램을 구축하기 위한 "프레임워크"는 아직 없습니다. 이러한 이유로 우리는 경험을 바탕으로 Pinocchio 프로그램을 작성하는 가장 좋은 방법이라고 믿는 것을 제시할 것입니다.

<ArticleSection name="진입점" id="entrypoint" level="h2" />

Anchor에서 `#[program]` 매크로는 많은 배선을 숨깁니다. 내부적으로 모든 명령어 및 계정 구조체에 대해 8바이트 구별자(버전 0.31부터 크기 사용자 정의 가능)를 구축합니다.

<AnchorDiscriminatorCalculator value={"Test"} />

네이티브 프로그램은 일반적으로 더 간결하게 유지합니다. 단일 바이트 구별자(값 0x01…0xFF)는 최대 255개의 명령어에 충분하며, 이는 대부분의 사용 사례에 충분합니다. 더 많이 필요하다면 2바이트 변형으로 전환하여 65,535개의 가능한 변형으로 확장할 수 있습니다.

`entrypoint!` 매크로는 프로그램 실행이 시작되는 곳입니다. 세 가지 원시 슬라이스를 제공합니다:
- **program_id**: 배포된 프로그램의 공개 키
- **accounts**: 명령어에 전달된 모든 계정
- **instruction_data**: 구별자와 사용자가 제공한 데이터를 포함하는 불투명 바이트 배열

즉, 진입점 이후에 적절한 핸들러를 통해 모든 다른 명령어를 실행하는 패턴을 만들 수 있으며, 이를 `process_instruction`이라고 부를 것입니다. 일반적으로 다음과 같습니다:

```rust
entrypoint!(process_instruction);

fn process_instruction(
    _program_id: &Pubkey,
    accounts: &[AccountInfo],
    instruction_data: &[u8],
) -> ProgramResult {    
    match instruction_data.split_first() {
        Some((Instruction1::DISCRIMINATOR, data)) => Instruction1::try_from((data, accounts))?.process(),
        Some((Instruction2::DISCRIMINATOR, _)) => Instruction2::try_from(accounts)?.process(),
        _ => Err(ProgramError::InvalidInstructionData)
    }
}
```

배후에서 이 핸들러는:
1. `split_first()`를 사용하여 구별자 바이트를 추출합니다.
2. `match`를 사용하여 인스턴스화할 명령어 구조체를 결정합니다.
3. 각 명령어의 `try_from` 구현은 입력을 검증하고 역직렬화합니다.
4. `process()` 호출은 비즈니스 로직을 실행합니다.

### `solana-program`과 `pinocchio`의 차이점

주요 차이점과 최적화는 `entrypoint()`가 작동하는 방식에 있습니다.
- 표준 Solana 진입점은 런타임이 입력 데이터를 미리 역직렬화하여 메모리에 소유된 데이터 구조를 생성하는 기존 직렬화 패턴을 사용합니다. 이 접근 방식은 Borsh 직렬화를 광범위하게 사용하고, 역직렬화 중에 데이터를 복사하며, 구조화된 데이터 유형을 위해 메모리를 할당합니다.
- Pinocchio 진입점은 복사 없이 입력 바이트 배열에서 직접 데이터를 읽어 제로 카피 작업을 구현합니다. 프레임워크는 원본 데이터를 참조하는 제로 카피 유형을 정의하고, 직렬화/역직렬화 오버헤드를 제거하며, 직접 메모리 액세스를 사용하여 추상화 계층을 피합니다.

<ArticleSection name="계정과 명령어" id="accounts-and-instructions" level="h2" />

매크로가 없고 프로그램을 간결하고 효율적으로 유지하기 위해 매크로를 피하고 싶으므로, 명령어 데이터와 계정의 모든 바이트를 수동으로 검증해야 합니다.

이 과정을 체계적으로 유지하기 위해 Rust의 `TryFrom` 특성을 구현하여 실제 `process()` 메서드를 거의 상용구 없이 유지하면서 매크로 없이 Anchor 스타일의 인체 공학을 제공하는 패턴을 사용합니다.

### `TryFrom` 특성 (The `TryFrom` Trait)

`TryFrom`은 Rust의 표준 변환 패밀리의 일부입니다. 변환이 실패할 수 없다고 가정하는 `From`과 달리 `TryFrom`은 `Result`를 반환하여 오류를 조기에 표면화할 수 있어 온체인 검증에 완벽합니다.

특성은 다음과 같이 정의됩니다:

```rust
pub trait TryFrom<T>: Sized {
    type Error;
    fn try_from(value: T) -> Result<Self, Self::Error>;
}
```

Solana 프로그램에서는 모든 제약 조건을 강제하면서 원시 계정 슬라이스(및 필요한 경우 명령어 바이트)를 강력한 유형의 구조체로 변환하기 위해 `TryFrom`을 구현합니다.

<ArticleSection name="계정 검증" id="accounts-validation" level="h2" />

우리는 일반적으로 각 `TryFrom` 구현에서 이중 차용(계정 검증과 프로세스 모두에서 차용할 가능성이 있음)이 필요하지 않은 모든 특정 검사를 처리합니다. 이렇게 하면 모든 명령어 로직이 발생하는 `process()` 함수를 가능한 한 깨끗하게 유지할 수 있습니다.

Anchor의 `Context`와 유사하게 명령어에 필요한 계정 구조체를 구현하는 것으로 시작합니다.

**참고**: Anchor와 달리 이 계정 구조체에는 프로세스에서 사용하려는 계정만 포함하고, 명령어에는 필요하지만 사용되지 않을 나머지 계정(예: `SystemProgram`)은 `_`로 표시합니다.

`Vault`와 같은 경우 다음과 같이 보일 수 있습니다:

```rust
pub struct DepositAccounts<'a> {
    pub owner: &'a AccountInfo,
    pub vault: &'a AccountInfo,
}
```

이제 명령어에서 어떤 계정을 사용하고 싶은지 알았으므로 `TryFrom` 특성을 사용하여 역직렬화하고 필요한 모든 검사를 수행할 수 있습니다:

```rust
impl<'a> TryFrom<&'a [AccountInfo]> for DepositAccounts<'a> {
    type Error = ProgramError;

    fn try_from(accounts: &'a [AccountInfo]) -> Result<Self, Self::Error> {
        // 1. 슬라이스 구조 분해
        let [owner, vault, _] = accounts else {
            return Err(ProgramError::NotEnoughAccountKeys);
        };

        // 2. 사용자 정의 검사
        if !owner.is_signer() {
            return Err(ProgramError::InvalidAccountOwner);
        }

        if !vault.is_owned_by(&pinocchio_system::ID) {
            return Err(ProgramError::InvalidAccountOwner);
        }

        // 3. 검증된 구조체 반환
        Ok(Self { owner, vault })
    }
}
```

보시다시피 이 명령어에서는 소유자에서 볼트로 Lamport를 전송하기 위해 `SystemProgram` CPI를 사용할 것이지만, 명령어 자체에서는 SystemProgram을 사용할 필요가 없습니다. 프로그램은 명령어에 포함되기만 하면 되므로 `_`로 전달할 수 있습니다.

그런 다음 Anchor의 `Signer` 및 `SystemAccount` 검사와 유사하게 계정에 대한 사용자 정의 검사를 수행하고 검증된 구조체를 반환합니다.

<ArticleSection name="명령어 검증" id="instruction-validation" level="h2" />

명령어 검증은 계정 검증과 유사한 패턴을 따릅니다. `TryFrom` 특성을 사용하여 명령어 데이터를 검증하고 강력한 유형의 구조체로 역직렬화하여 `process()`의 비즈니스 로직을 깨끗하고 집중적으로 유지합니다.

명령어 데이터를 나타내는 구조체를 정의하는 것으로 시작하겠습니다:

```rust
pub struct DepositInstructionData {
    pub amount: u64,
}
```

그런 다음 `TryFrom`을 구현하여 명령어 데이터를 검증하고 구체적인 유형으로 변환합니다. 여기에는 다음이 포함됩니다:
1. 데이터 길이가 예상 크기와 일치하는지 확인
2. 바이트 슬라이스를 구체적인 유형으로 변환
3. 필요한 검증 검사 수행

구현 모습은 다음과 같습니다:

```rust
impl<'a> TryFrom<&'a [u8]> for DepositInstructionData {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        // 1. 데이터 길이가 u64(8바이트)와 일치하는지 확인
        if data.len() != core::mem::size_of::<u64>() {
            return Err(ProgramError::InvalidInstructionData);
        }

        // 2. 바이트 슬라이스를 u64로 변환
        let amount = u64::from_le_bytes(data.try_into().unwrap());

        // 3. 금액 검증 (예: 0이 아닌지 확인)
        if amount == 0 {
            return Err(ProgramError::InvalidInstructionData);
        }

        Ok(Self { amount })
    }
}
```

이 패턴을 통해 다음을 수행할 수 있습니다:
- 비즈니스 로직에 도달하기 전에 명령어 데이터 검증
- 검증 로직을 핵심 기능과 분리
- 검증 실패 시 명확한 오류 메시지 제공
- 프로그램 전체에서 타입 안전성 유지
