# 계정 (Accounts)

우리는 `#[account]` 매크로를 보았지만, 당연히 Solana에는 다양한 유형의 계정이 존재합니다. 이러한 이유로 Solana에서 계정이 일반적으로 어떻게 작동하는지, 그리고 더 깊이 들어가서 Anchor와 함께 어떻게 작동하는지 살펴볼 가치가 있습니다.

<ArticleSection name="일반적인 개요" id="general-overview" level="h2" />

Solana에서 모든 상태(state)는 계정에 존재합니다. [원장(ledger)](https://solana.com/docs/references/terminology#ledger)을 각 행이 동일한 기본 스키마를 공유하는 하나의 거대한 테이블로 상상해 보세요:

```rust
pub struct Account {
    /// 계정에 있는 lamports
    pub lamports: u64,
    /// 이 계정에 보관된 데이터
    #[cfg_attr(feature = "serde", serde(with = "serde_bytes"))]
    pub data: Vec<u8>,
    /// 이 계정을 소유하고 lamports나 데이터를 변경할 수 있는 프로그램
    pub owner: Pubkey,
    /// 계정이 프로그램이면 `true`, 단순히 프로그램에 속한 것이면 `false`
    pub executable: bool,
    /// 이 계정이 다음에 임대료(rent)를 내야 하는 에포크 (현재는 더 이상 사용되지 않으며 `0`으로 설정됨)
    pub rent_epoch: Epoch,
}
```

Solana의 모든 계정은 동일한 기본 레이아웃을 공유합니다. 차이점은 다음과 같습니다:

1. 소유자(Owner): 계정의 데이터와 lamport를 수정할 수 있는 독점적인 권한을 가진 프로그램.
2. 데이터(Data): 소유자 프로그램이 서로 다른 계정 유형을 구별하는 데 사용합니다.

우리가 토큰 프로그램 계정을 이야기할 때, 이는 `owner`가 토큰 프로그램인 계정을 의미합니다. 데이터 필드가 비어 있는 시스템 계정과 달리, 토큰 프로그램 계정은 **Mint** 계정이거나 **Token** 계정일 수 있습니다. 우리는 이들을 구별하기 위해 식별자(discriminator)를 사용합니다.

토큰 프로그램이 계정을 소유할 수 있는 것처럼, 우리 자신의 프로그램을 포함한 다른 어떤 프로그램도 계정을 소유할 수 있습니다.

<ArticleSection name="프로그램 계정" id="program-accounts" level="h2" />

프로그램 계정은 Anchor 프로그램에서 상태 관리의 기초입니다. 이를 통해 프로그램이 소유하는 커스텀 데이터 구조를 만들 수 있습니다. 이를 효과적으로 사용하는 방법을 알아봅시다.

### 계정 구조와 식별자 (Discriminators)

Anchor의 모든 프로그램 계정은 자신의 유형을 식별할 방법이 필요합니다. 이는 식별자를 통해 처리되며, 두 가지 방법이 있습니다:

1. **기본 식별자**: 계정의 경우 `sha256("account:<StructName>")[0..8]`, 명령어의 경우 `sha256("global:<instruction_name>")[0..8]`을 사용하여 생성된 8바이트 접두사입니다. 시드(seeds)는 계정의 경우 PascalCase를, 명령어의 경우 snake_case를 사용합니다.

<AnchorDiscriminatorCalculator value={"TestAccount"} displayMode="account" />

2. **커스텀 식별자**: Anchor `v0.31.0`부터는 자신만의 식별자를 지정할 수 있습니다:

```rust
#[account(discriminator = 1)]              // 단일 바이트
pub struct Escrow { … }
```

**식별자에 대한 중요 참고 사항**:
- 프로그램 전체에서 고유해야 합니다.
- `[1]`을 사용하면 `[1, 2, …]`와 같이 `1`로 시작하는 다른 식별자를 사용할 수 없습니다.
- `[0]`은 초기화되지 않은 계정과 충돌하므로 사용할 수 없습니다.

### 프로그램 계정 생성하기

프로그램 계정을 생성하려면 먼저 데이터 구조를 정의합니다:

```rust
use anchor_lang::prelude::*;

#[derive(InitSpace)]
#[account(discriminator = 1)]
pub struct CustomAccountType {
    data: u64,
}
```

프로그램 계정의 핵심 사항:
- 최대 크기는 10,240 바이트 (10 KiB)입니다.
- 더 큰 계정의 경우 `zero_copy`와 청크(chunked) 쓰기가 필요합니다.
- `InitSpace` derive 매크로는 필요한 공간을 자동으로 계산합니다.
- 총 공간 = `INIT_SPACE` + `DISCRIMINATOR.len()`

계정에 필요한 바이트 단위의 총 공간은 `INIT_SPACE` (모든 필드 크기의 합)와 식별자 크기 (`DISCRIMINATOR.len()`)의 합입니다.

Solana 계정은 계정 크기에 따라 lamport 보증금(rent deposit)이 필요합니다. 크기를 알면 계정을 개설하기 위해 얼마나 많은 lamport를 예치해야 하는지 계산할 수 있습니다.

`Account` 구조체에서 계정을 초기화하는 방법은 다음과 같습니다:

```rust
#[account(
    init,
    payer = <target_account>,
    space = <num_bytes>                 // CustomAccountType::INIT_SPACE + CustomAccountType::DISCRIMINATOR.len(),
)]
pub account: Account<'info, CustomAccountType>,
```

이미 다룬 `seeds`와 `bump` 필드 외에 `#[account]` 매크로에서 사용되는 몇 가지 필드와 그 역할은 다음과 같습니다:
- `init`: Anchor에게 계정을 생성하라고 지시합니다.
- `payer`: 임대료를 부담하는 서명자 (여기서는 maker)
- `space`: 할당할 바이트 수. 여기서 임대료 계산도 이루어집니다.

생성 후에는 계정의 데이터를 수정할 수 있습니다. 크기를 변경해야 하는 경우 재할당(reallocation)을 사용하세요:

```rust
#[account(
    mut,                       // 변경 가능으로 표시
    realloc = <space>,         // 새로운 크기
    realloc::payer = <target>, // 변경 비용 지불자
    realloc::zero = <bool>     // 새로운 공간을 0으로 초기화할지 여부
)]
```

**참고**: 계정 크기를 줄일 때는 `realloc::zero = true`로 설정하여 이전 데이터가 적절히 지워지도록 하세요.

마지막으로, 계정이 더 이상 필요하지 않을 때 닫아서 임대료를 회수할 수 있습니다:

```rust
#[account(
    mut,                       // 변경 가능으로 표시
    close = <target_account>,  // 남은 lamport를 보낼 곳
)]
pub account: Account<'info, CustomAccountType>,
```

그런 다음 `seeds`와 프로그램 ID에서 파생된 결정론적 주소인 PDA를 이러한 제약 조건에 추가할 수 있습니다. 이는 예측 가능한 계정 주소를 만드는 데 특히 유용합니다:

```rust
#[account(
    seeds = <seeds>,            // 파생을 위한 시드
    bump                        // 표준 범프 시드
)]
pub account: Account<'info, CustomAccountType>,
```

**참고**: PDA는 결정론적입니다: 같은 시드 + 프로그램 + 범프는 항상 같은 주소를 생성하며, 범프는 주소가 ed25519 곡선 밖에 있도록 보장합니다.

범프를 계산하는 것은 많은 CU를 소모할 수 있으므로, 매번 계산하는 대신 계정에 저장하거나 명령어로 전달하여 검증하는 것이 좋습니다:

```rust
#[account(
    seeds = <seeds>,
    bump = <expr>
)]
pub account: Account<'info, CustomAccountType>,
```

그리고 다른 프로그램에서 파생된 PDA를 해당 프로그램의 주소를 전달하여 파생할 수도 있습니다:

```rust
#[account(
    seeds = <seeds>,
    bump = <expr>,
    seeds::program = <expr>
)]
pub account: Account<'info, CustomAccountType>,
```

### Lazy Account

Anchor 0.31.0부터 `LazyAccount`는 계정 데이터를 읽는 더 성능 좋은 방법을 제공합니다. 전체 계정을 스택에 역직렬화하는 표준 `Account` 타입과 달리, `LazyAccount`는 읽기 전용이며 힙에 할당된 계정으로, 스택 메모리를 24바이트만 사용하며 특정 필드만 선택적으로 로드할 수 있게 해줍니다.

`Cargo.toml`에서 기능을 활성화하여 시작하세요:

```
anchor-lang = { version = "0.31.1", features = ["lazy-account"] }
```

이제 다음과 같이 사용할 수 있습니다:

```rust
#[derive(Accounts)]
pub struct MyInstruction<'info> {
    pub account: LazyAccount<'info, CustomAccountType>,
}

#[account(discriminator = 1)]
pub struct CustomAccountType {
    pub balance: u64,
    pub metadata: String,
}

pub fn handler(ctx: Context<MyInstruction>) -> Result<()> {
    // 특정 필드 로드
    let balance = ctx.accounts.account.get_balance()?;
    let metadata = ctx.accounts.account.get_metadata()?;
    
    Ok(())
}
```

> `LazyAccount`는 읽기 전용입니다. 스택에 할당된 데이터가 아니라 참조로 작업하기 때문에 필드를 변경하려고 하면 패닉이 발생합니다.

CPI가 계정을 수정하면 캐시된 값은 오래된 값이 됩니다. 이러한 이유로 새로 고치려면 `unload()` 함수를 사용해야 합니다:

```rust
// 초기 값 로드
let initial_value = ctx.accounts.my_account.load_field()?;

// CPI 수행...

// `initial_value`로부터 계정에 대한 참조를 여전히 가지고 있으므로 `unload` 전에 drop
drop(initial_value);

// 업데이트된 값 로드
let updated_value = ctx.accounts.my_account.unload()?.load_field()?;
```

<ArticleSection name="토큰 계정" id="token-program" level="h2" />

Solana 프로그램 라이브러리(SPL)의 일부인 토큰 프로그램은 네이티브 SOL이 아닌 모든 자산을 발행하고 이동하기 위한 내장 툴킷입니다. 토큰 생성, 새로운 공급량 발행, 잔액 전송, 소각, 동결 등을 위한 명령어를 가지고 있습니다.

이 프로그램은 두 가지 핵심 계정 유형을 소유합니다:
- **Mint 계정**: 특정 토큰에 대한 메타데이터(공급량, 소수점 자리수, 민트 권한, 동결 권한 등)를 저장합니다.
- **Token 계정**: 특정 소유자의 해당 민트 잔액을 보유합니다. 소유자만이 잔액을 줄일 수 있지만(전송, 소각 등), 누구나 계정으로 토큰을 보내 잔액을 늘릴 수 있습니다.

### Anchor에서의 토큰 계정

기본적으로 핵심 Anchor 크레이트는 시스템 프로그램을 위한 CPI 및 계정 도우미만 번들로 제공합니다. SPL 토큰에 대해서도 같은 지원을 원한다면 `anchor_spl` 크레이트를 가져와야 합니다.

`anchor_spl`이 추가하는 것:
- SPL Token 및 Token-2022 프로그램의 모든 명령어에 대한 도우미 빌더
- Mint 및 Token 계정을 고통 없이 검증하고 역직렬화할 수 있는 타입 래퍼(wrappers)

`Mint`와 `Token` 계정이 어떻게 구성되는지 살펴봅시다:

```rust
#[account(
    mint::decimals     = <expr>,
    mint::authority    = <target_account>,
    mint::freeze_authority = <target_account>
    mint::token_program = <target_account>
)]
pub mint: Account<'info, Mint>,

#[account(
    mut,
    associated_token::mint       = <target_account>,
    associated_token::authority  = <target_account>,
    associated_token::token_program = <target_account>
)]
pub maker_ata_a: Account<'info, TokenAccount>,
```

`Account<'info, Mint>`와 `Account<'info, TokenAccount>`는 Anchor에게 다음을 지시합니다:
- 계정이 실제로 Mint 또는 Token 계정인지 확인
- 데이터를 역직렬화하여 필드를 직접 읽을 수 있게 함
- 지정한 추가 제약 조건(`authority`, `decimals`, `mint`, `token_program` 등)을 강제

이러한 토큰 관련 계정들은 앞서 사용한 것과 동일한 `init` 패턴을 따릅니다. Anchor는 이들의 고정된 바이트 크기를 알고 있으므로, `space` 값을 지정할 필요 없이 계정에 자금을 대는 `payer`만 지정하면 됩니다.

Anchor는 또한 `init_if_needed` 매크로를 제공합니다: 토큰 계정이 이미 존재하는지 확인하고, 없으면 생성합니다. 이 단축키는 모든 계정 유형에 안전한 것은 아니지만, 토큰 계정에는 완벽하게 적합하므로 여기서 사용할 것입니다.

언급했듯이, `anchor_spl`은 **Token** 및 **Token2022** 프로그램 모두에 대한 도우미를 생성하며, 후자는 토큰 확장을 도입합니다. 주요 과제는 이 계정들이 유사한 목표를 달성하고 유사한 구조를 가지고 있음에도 불구하고, 서로 다른 두 프로그램이 소유하기 때문에 동일한 방식으로 역직렬화하고 확인할 수 없다는 것입니다.

이러한 다른 계정 유형을 처리하기 위해 더 "고급" 로직을 만들 수 있지만, 다행히도 Anchor는 **InterfaceAccounts**를 통해 이 시나리오를 지원합니다:

```rust
use anchor_spl::token_interface::{Mint, TokenAccount};

#[account(
    mint::decimals     = <expr>,
    mint::authority    = <target_account>,
    mint::freeze_authority = <target_account>
)]
pub mint: InterfaceAccounts<'info, Mint>,

#[account(
    mut,
    associated_token::mint = <target_account>,
    associated_token::authority = <target_account>,
    associated_token::token_program = <target_account>
)]
pub maker_ata_a: InterfaceAccounts<'info, TokenAccount>,
```

여기서의 핵심 차이점은 `Account` 대신 `InterfaceAccounts`를 사용한다는 것입니다. 이를 통해 우리 프로그램은 역직렬화 로직의 차이를 처리할 필요 없이 Token 및 Token2022 계정 모두와 작업할 수 있습니다. 인터페이스는 타입 안전성과 적절한 검증을 유지하면서 두 유형의 계정과 상호 작용할 수 있는 공통된 방법을 제공합니다.

이 접근 방식은 각 프로그램에 대해 별도의 로직을 작성할 필요가 없으므로 두 토큰 표준과 호환되는 프로그램을 원할 때 특히 유용합니다. 인터페이스는 장면 뒤에서 서로 다른 계정 구조를 처리하는 모든 복잡성을 처리합니다.

`anchor-spl` 사용법에 대해 더 알고 싶다면 [Anchor로 배우는 SPL-Token 프로그램](/ko/courses/spl-token-with-anchor) 또는 [Anchor로 배우는 Token2022 프로그램](/ko/courses/token-2022-with-anchor) 코스를 따라갈 수 있습니다.

<ArticleSection name="추가 계정 유형" id="additional-accounts-type" level="h2" />

당연히 시스템 계정, 프로그램 계정, 토큰 계정이 Anchor에서 가질 수 있는 유일한 계정 유형은 아닙니다. 여기서 가질 수 있는 다른 유형의 계정을 살펴보겠습니다:

### Signer

`Signer` 타입은 계정이 트랜잭션에 서명했는지 확인해야 할 때 사용됩니다. 이는 특정 계정만이 특정 작업을 수행할 수 있도록 보장하므로 보안에 매우 중요합니다. 자금 이체나 명시적인 허가가 필요한 계정 데이터 수정과 같이 특정 계정이 트랜잭션을 승인했음을 보장해야 할 때마다 이 타입을 사용합니다. 사용 방법은 다음과 같습니다:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    #[account(mut)]
    pub signer: Signer<'info>,
}
```

`Signer` 타입은 계정이 트랜잭션에 서명했는지 자동으로 확인합니다. 서명하지 않았다면 트랜잭션은 실패합니다. 이는 특정 계정만 특정 작업을 수행할 수 있도록 해야 할 때 특히 유용합니다.

### AccountInfo & UncheckedAccount

`AccountInfo`와 `UncheckedAccount`는 자동 검증 없이 계정 데이터에 직접 접근할 수 있는 로우 레벨 계정 타입입니다. 기능적으로는 동일하지만, 이름이 그 목적을 더 잘 반영하는 `UncheckedAccount`가 선호되는 선택입니다.

이 타입들은 주로 세 가지 시나리오에서 유용합니다:
1. 정의된 구조가 없는 계정 작업
2. 커스텀 검증 로직 구현
3. Anchor 타입 정의가 없는 다른 프로그램의 계정과 상호 작용

이 타입들은 Anchor의 안전성 검사를 우회하므로 본질적으로 안전하지 않으며 `/// CHECK` 주석을 사용하여 명시적인 승인이 필요합니다. 이 주석은 여러분이 위험을 이해하고 적절한 검증을 구현했음을 문서화하는 역할을 합니다.

사용 예시는 다음과 같습니다:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    /// CHECK: This is an unchecked account
    pub account: UncheckedAccount<'info>,

    /// CHECK: This is an unchecked account
    pub account_info: AccountInfo<'info>,
}
```

### Option

Anchor의 `Option` 타입을 사용하면 명령어에서 계정을 선택 사항으로 만들 수 있습니다. 계정이 `Option`으로 래핑되면 트랜잭션에서 제공되거나 생략될 수 있습니다. 이는 다음과 같은 경우에 특히 유용합니다:
- 특정 계정이 있거나 없이도 작동할 수 있는 유연한 명령어 구축
- 항상 필요하지 않을 수 있는 선택적 매개변수 구현
- 새 계정 구조나 이전 계정 구조와 작동할 수 있는 하위 호환 명령어 생성

`Option` 계정이 `None`으로 설정되면, Anchor는 프로그램 ID를 계정 주소로 사용합니다. 선택적 계정으로 작업할 때 이 동작을 이해하는 것이 중요합니다.

구현 방법은 다음과 같습니다:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub optional_account: Option<Account<'info, CustomAccountType>>,
}
```

### Box

`Box` 타입은 계정을 스택 대신 힙에 저장하는 데 사용됩니다. 이는 여러 시나리오에서 필요합니다:
- 스택에 저장하기 비효율적인 큰 계정 구조를 다룰 때
- 재귀적 데이터 구조를 다룰 때
- 컴파일 타임에 크기를 결정할 수 없는 계정을 다룰 때

`Box`를 사용하면 힙에 계정 데이터를 할당하여 이러한 경우에 메모리를 더 효율적으로 관리할 수 있습니다. 예시는 다음과 같습니다:

```rust
#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub boxed_account: Box<Account<'info, LargeAccountType>>,
}
```

### Program

`Program` 타입은 다른 Solana 프로그램을 검증하고 상호 작용하는 데 사용됩니다. Anchor는 `executable` 플래그가 `true`로 설정되어 있기 때문에 프로그램 계정을 쉽게 식별할 수 있습니다. 이 타입은 다음과 같은 경우에 특히 유용합니다:

- 교차 프로그램 호출(CPI)을 수행해야 할 때
- 올바른 프로그램과 상호 작용하고 있는지 확인하고 싶을 때
- 계정의 프로그램 소유권을 확인해야 할 때

`Program` 타입을 사용하는 두 가지 주요 방법이 있습니다:

1. 내장 프로그램 타입 사용 (가능한 경우 권장):
```rust
use anchor_spl::token::Token;

#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub system_program: Program<'info, System>,
    pub token_program: Program<'info, Token>,
}
```

2. 프로그램 타입을 사용할 수 없을 때 커스텀 프로그램 주소 사용:
```rust
// 프로그램 주소
const PROGRAM_ADDRESS: Pubkey = pubkey!("22222222222222222222222222222222222222222222")

#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    #[account(address = PROGRAM_ADDRESS)]
    /// CHECK: this is fine since we're checking the address
    pub program: UncheckedAccount<'info>,
}
```

**참고**: 토큰 프로그램으로 작업할 때, 레거시 토큰 프로그램과 Token-2022 프로그램 모두를 지원해야 할 수도 있습니다. 이런 경우 `Program` 대신 `Interface` 타입을 사용하세요:

```rust
use anchor_spl::token_interface::TokenInterface;

#[derive(Accounts)]
pub struct InstructionAccounts<'info> {
    pub program: Interface<'info, TokenInterface>,
}
```

<ArticleSection name="커스텀 계정 검증" id="custom-account-validation" level="h2" />

Anchor는 `#[account]` 속성에 직접 적용할 수 있는 강력한 제약 조건 세트를 제공합니다. 이 제약 조건들은 명령어 로직이 실행되기 전에, 계정 수준에서 계정의 유효성을 보장하고 프로그램 규칙을 강제하는 데 도움이 됩니다. 사용 가능한 제약 조건은 다음과 같습니다:

### 주소(Address) 제약 조건

`address` 제약 조건은 계정의 공개 키가 특정 값과 일치하는지 확인합니다. 이는 특정 PDA나 프로그램 계정과 같이 알려진 계정과 상호 작용하고 있는지 확인해야 할 때 필수적입니다:

```rust
#[account(
    address = <expr>,                    // 기본 사용법
    address = <expr> @ CustomError       // 커스텀 에러 포함
)]
pub account: Account<'info, CustomAccountType>,
```

### 소유자(Owner) 제약 조건

`owner` 제약 조건은 계정이 특정 프로그램에 의해 소유되었는지 확인합니다. 이는 프로그램 소유 계정으로 작업할 때 중요한 보안 검사로, 특정 프로그램이 관리해야 하는 계정에 대한 무단 접근을 방지합니다:

```rust
#[account(
    owner = <expr>,                      // 기본 사용법
    owner = <expr> @ CustomError         // 커스텀 에러 포함
)]
pub account: Account<'info, CustomAccountType>,
```

### 실행 가능(Executable) 제약 조건

`executable` 제약 조건은 계정이 프로그램 계정인지(`executable` 플래그가 `true`로 설정되어 있는지) 확인합니다. 이는 데이터 계정이 아닌 프로그램과 상호 작용하고 있는지 확인하기 위해 교차 프로그램 호출(CPI)을 할 때 특히 유용합니다:

```rust
#[account(executable)]
pub account: Account<'info, CustomAccountType>,
```

### 변경 가능(Mutable) 제약 조건

`mut` 제약 조건은 계정을 변경 가능으로 표시하여 명령어 실행 중에 데이터가 수정될 수 있도록 합니다. Anchor는 안전을 위해 기본적으로 불변성을 강제하므로 업데이트될 모든 계정에 대해 이 조건이 필요합니다:

```rust
#[account(
    mut,                                 // 기본 사용법
    mut @ CustomError                    // 커스텀 에러 포함
)]
pub account: Account<'info, CustomAccountType>,
```

### 서명자(Signer) 제약 조건

`signer` 제약 조건은 계정이 트랜잭션에 서명했는지 확인합니다. 자금 이체나 데이터 수정과 같이 행동을 승인해야 할 때 보안에 중요합니다. `Signer` 타입을 사용하는 것보다 서명을 요구하는 더 명시적인 방법입니다:

```rust
#[account(
    signer,                              // 기본 사용법
    signer @ CustomError                 // 커스텀 에러 포함
)]
pub account: Account<'info, CustomAccountType>,
```

### Has One 제약 조건

`has_one` 제약 조건은 계정 구조체의 특정 필드가 다른 계정의 공개 키와 일치하는지 확인합니다. 토큰 계정이 올바른 소유자에게 속해 있는지 확인하는 등 계정 간의 관계를 유지하는 데 유용합니다:

```rust
#[account(
    has_one = data @ Error::InvalidField
)]
pub account: Account<'info, CustomAccountType>,
```

### 커스텀 제약 조건

내장 제약 조건이 요구 사항을 충족하지 못할 때, 커스텀 검증 표현식을 작성할 수 있습니다. 이를 통해 계정 데이터 길이 확인이나 여러 필드 간의 관계 검증과 같이 다른 제약 조건으로는 표현할 수 없는 복잡한 검증 로직이 가능해집니다:

```rust
#[account(
    constraint = data == account.data @ Error::InvalidField
)]
pub account: Account<'info, CustomAccountType>,
```

이러한 제약 조건들을 조합하여 계정에 대한 강력한 검증 규칙을 만들 수 있습니다. 계정 수준에 검증을 배치함으로써 보안 검사를 계정 정의에 가깝게 유지하고 명령어 로직 전체에 `require!()` 호출이 흩어지는 것을 방지할 수 있습니다.

<ArticleSection name="남은 계정 (Remaining Accounts)" id="remaining-accounts" level="h2" />

프로그램을 작성할 때, 고정된 명령어 계정 구조가 프로그램에 필요한 유연성을 제공하지 못하는 경우가 있습니다.

남은 계정(Remaining accounts)은 정의된 명령어 구조 이외의 추가 계정을 전달할 수 있게 하여 런타임 조건에 따른 동적 동작을 가능하게 함으로써 이 문제를 해결합니다.

### 구현 가이드라인

전통적인 명령어 정의는 어떤 계정이 사용될지 정확히 지정해야 합니다:

```rust
#[derive(Accounts)]
pub struct Transfer<'info> {
    pub from: Account<'info, TokenAccount>,
    pub to: Account<'info, TokenAccount>,
    pub authority: Signer<'info>,
}
```

이는 단일 작업에는 잘 작동하지만, 한 번의 명령어로 여러 토큰 전송을 수행하고 싶다면 어떻게 해야 할까요? 명령어를 여러 번 호출해야 하며, 이는 트랜잭션 비용과 복잡성을 증가시킵니다.

남은 계정을 사용하면 고정된 명령어 구조의 일부가 아닌 추가 계정을 전달할 수 있습니다. 즉, 프로그램이 이 계정들을 반복하고 로직을 동적으로 반복 적용할 수 있다는 의미입니다.

각 전송에 대해 별도의 명령어를 요구하는 대신, "N" 번의 전송을 처리하는 하나의 명령어를 설계할 수 있습니다:

```rust
#[derive(Accounts)]
pub struct BatchTransfer<'info> {
    pub from: Account<'info, TokenAccount>,
    pub to: Account<'info, TokenAccount>,
    pub authority: Signer<'info>,
}

pub fn batch_transfer(ctx: Context<BatchTransfer>, amounts: Vec<u64>) -> Result<()> {
    // 고정 계정을 사용하여 첫 번째 전송 처리
    transfer_tokens(&ctx.accounts.from, &ctx.accounts.to, amounts[0])?;
    
    let remaining_accounts = &ctx.remaining_accounts;

    // 중요: 남은 계정 스키마 검증
    // 배치 전송의 경우 계정 쌍을 예상합니다
    require!(
        remaining_accounts.len() % 2 == 0,
        TransferError::InvalidRemainingAccountsSchema
    );

    // 남은 계정을 2개씩 묶어서 처리 (from_account, to_account)
    for (i, chunk) in remaining_accounts.chunks(2).enumerate() {
        let from_account = &chunk[0];
        let to_account = &chunk[1];
        let amount = amounts[i + 1];
        
        // 남은 계정에 동일한 전송 로직 적용
        transfer_tokens(from_account, to_account, amount)?;
    }
    
    Ok(())
}
```

명령어 배칭(Batching)의 의미:
- 더 작은 명령어 크기: 반복되는 계정과 데이터가 포함될 필요가 없음
- 효율성: 각 CPI 비용은 1000 CU이므로, 누군가 배치 명령어를 수행해야 할 때 3번 대신 1번만 호출하면 됨

> 남은 계정은 `UncheckedAccount`로 전달됩니다. 즉, Anchor는 이에 대해 어떤 검증도 수행하지 않습니다. 항상 `RemainingAccountSchema`와 기본 계정을 검증하세요.

### 클라이언트 사이드 구현

`anchor build`를 통해 생성된 Anchor SDK를 사용하면 남은 계정을 쉽게 전달할 수 있습니다. 이들은 "원시(raw)" 계정이므로 서명자 여부 및/또는 변경 가능 여부를 다음과 같이 지정해야 합니다:

```ts
await program.methods.someMethod().accounts({
  // 일부 계정
})
.remainingAccounts([
  {
    isSigner: false,
    isWritable: true,
    pubkey: new Pubkey().default
  }
])
.rpc();
```
