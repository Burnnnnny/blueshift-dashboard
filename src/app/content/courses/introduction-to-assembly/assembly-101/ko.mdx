# sBPF 어셈블리 101 (sBPF Assembly 101)

![어셈블리 소개](/graphics/course-banners/introduction-to-assembly.png)

sBPF 어셈블리와 Solana 프로그램에서의 역할을 이해하려면 우선 어셈블리 언어와 그것이 고수준 코드와 기계 실행을 어떻게 연결하는지 이해해야 합니다.

<ArticleSection name="어셈블리 언어" id="the-assembly-language" level="h2" />

어셈블리는 기계 코드의 사람이 읽을 수 있는 형태입니다. 즉, 프로세서가 실행하는 실제 명령어입니다. 이는 고수준 프로그래밍 언어와 컴퓨터가 이해하는 이진 코드 사이의 다리 역할을 합니다.

다음과 같은 Rust 코드를 작성할 때:

```rust
let result = a + b;
```

컴파일러는 이를 여러 단계를 거쳐 변환합니다:
1. Rust 소스 → 구문 분석 및 분석
2. 중간 표현(Intermediate representation) → 최적화
3. 어셈블리 코드 → 사람이 읽을 수 있는 명령어
4. 기계 코드 → 프로세서가 실행하는 바이너리

어셈블리는 3단계를 차지합니다. 이진수로 변환되기 전의 마지막으로 사람이 읽을 수 있는 형식입니다. 각 어셈블리 명령어는 숫자 더하기, 메모리 로드 또는 다른 코드 섹션으로의 점프와 같은 정확히 하나의 프로세서 작업에 해당합니다.

<ArticleSection name="sBPF 가상 머신" id="the-sbpf-virtual-machine" level="h2" />

Solana sBPF는 모든 온체인 프로그램을 실행하는 확장된 버클리 패킷 필터(eBPF) 명령어 세트 및 가상 머신의 Solana 맞춤형 변형입니다. 이는 프로그램과 검증인의 기본 CPU 사이에 위치하는 64비트 레지스터 머신인 특수 실행 환경을 생성합니다.

sBPF를 블록체인 실행을 위해 설계된 특수 목적 컴퓨터라고 생각하세요. 높은 처리량의 트랜잭션을 처리할 만큼 빠르면서도 수천 명의 검증인 간에 보안과 결정론을 보장할 만큼 충분히 제약적입니다.

CPU에서 직접 실행되는 네이티브 어셈블리와 달리, sBPF 코드는 제어된 가상 머신 환경 내에서 실행됩니다. 이 가상 머신은 실행 전에 모든 명령어를 검증하여 충돌, 무한 루프 및 승인되지 않은 메모리 액세스를 방지함으로써 안전을 보장합니다.

이러한 안전 제약에도 불구하고, sBPF는 네이티브에 가까운 실행 속도를 달성하는 `just-in-time` 컴파일을 통해 고성능을 유지합니다.

가상 머신은 또한 결정론적 실행을 보장합니다. 동일한 입력에 대해 동일한 프로그램은 전 세계의 모든 검증인에서 동일한 결과를 생성합니다. 이러한 일관성은 블록체인 합의에 매우 중요합니다.

또한, sBPF는 계정 액세스, 프로그램 간 호출 및 런타임 상호 작용을 위한 syscall을 포함합니다.

### sBPF 어셈블리 이해가 중요한 이유

Rust 컴파일러가 고수준 코드를 sBPF 명령어로 효율적으로 변환하지만, 어셈블리를 이해하면 다음과 같은 이점이 있습니다:
- **컴퓨팅 비용 이해**: 모든 sBPF 명령어는 컴퓨팅 단위(CU)를 소비합니다. Rust 한 줄은 수백 개의 명령어로 컴파일될 수 있습니다. 어셈블리는 특정 작업이 왜 비싼지 보여줍니다.
- **더 작은 프로그램 크기**: sBPF 어셈블리로 직접 작성된 프로그램은 컴파일된 Rust 동등물보다 훨씬 작아서 배포 비용을 줄이고 로드 시간을 개선합니다.
- **최적화 기회**: Rust 컴파일러는 안전하고 올바른 코드를 생성하지만 항상 가장 효율적인 것은 아닙니다. 어셈블리는 중복 안전 검사 및 차선의 명령어 시퀀스를 노출합니다.
- **디버깅 및 분석**: 프로그램이 예상치 못하게 동작할 때 어셈블리는 근거를 제공합니다. 어떤 명령어가 실행되었는지 정확히 추적하고 실패 지점을 식별할 수 있습니다.

### 아키텍처

sBPF는 10개의 범용 레지스터, 하나의 읽기 전용 스택 포인터, 그리고 복잡한 주소 지정 모드가 없는 로드-스토어 아키텍처를 사용합니다.

이러한 단순함은 의도적입니다. 명령어 변형이 적을수록 더 빠른 검증, 더 빠른 JIT 컴파일 및 더 예측 가능한 성능이 가능합니다.

eBPF 프로그램이 커널에 로드될 때마다 바이트코드는 JIT 컴파일러에 의해 호스트 CPU 아키텍처에 특정한 네이티브 기계 명령어로 변환된 다음 VM에 의해 실행됩니다.

### 실행

sBPF 프로그램은 간단한 프로세스를 통해 실행됩니다. 프로그램 카운터(`PC`)는 명령어 목록의 책갈피처럼 다음에 실행할 명령어를 추적합니다.

실행 주기는 다음 단계를 따릅니다:
1. **가져오기 (Fetch)**: 프로그램 카운터에서 명령어 읽기
2. **디코딩 (Decode)**: 명령어 형식 및 피연산자 해석
3. **실행 (Execute)**: 작업 수행 (레지스터 수정, 메모리 액세스 또는 제어 흐름 변경)
4. **진행 (Advance)**: 프로그램 카운터를 다음 명령어로 이동 (또는 분기를 위해 점프)
5. **반복 (Repeat)**: 프로그램이 종료될 때까지 계속

각 명령어는 산술, 메모리 액세스, 비교 또는 함수 호출과 같은 정확히 하나의 작업을 수행합니다. 이러한 작업당 하나의 명령어 설계는 sBPF 프로그램을 예측 가능하고 분석 가능하게 만듭니다.

<ArticleSection name="JIT 컴파일러 파이프라인" id="the-jit-compiler-pipeline" level="h2" />

sBPF 프로그램은 Just-In-Time (JIT) 컴파일을 통해 고성능을 달성합니다.

프로그램을 Solana에 배포할 때 런타임은 두 가지 작업을 수행합니다:
- **검증 (Verification)**: 무한 루프, 잘못된 메모리 액세스 및 잠재적 충돌을 확인하여 프로그램 안전을 보장합니다. 검증기는 안전한 작동을 보장하기 위해 가능한 모든 실행 경로를 분석합니다.
- **컴파일 (Compilation)**: sBPF 명령어를 검증인의 CPU에서 직접 실행되는 네이티브 기계 코드로 변환합니다. `add64 r1, r2`와 같은 간단한 작업은 단일 네이티브 추가 명령어가 되고, 복잡한 작업은 추가 안전 검사를 받지만 여전히 효율적인 네이티브 코드로 컴파일됩니다.

이 접근 방식은 배포 시간을 실행 속도와 교환합니다. 프로그램은 배포 중 한 번 검증되고 컴파일되지만 수천 번 실행되므로 블록체인 성능에 대한 훌륭한 절충안이 됩니다.

JIT 검증 프로세스는 가능한 모든 프로그램 경로를 검토하여 메모리 액세스가 경계 내에 있는지, 점프가 유효한 주소를 대상으로 하는지, 실행이 컴퓨팅 제한 내에서 종료되는지 확인합니다.

JIT 컴파일 프로세스는 각 sBPF 명령어를 동등한 네이티브 CPU 명령어로 변환합니다. 대부분의 실행이 네이티브 코드에서 발생하므로 가상 머신 오버헤드는 최소화됩니다.

> sBPF가 네이티브 코드로 컴파일된다는 것을 이해하면 산술 연산은 빠르지만 런타임으로 넘어가는 syscall은 오버헤드가 있는 이유를 설명할 수 있습니다. 이 지식은 최적화 결정을 안내합니다.
