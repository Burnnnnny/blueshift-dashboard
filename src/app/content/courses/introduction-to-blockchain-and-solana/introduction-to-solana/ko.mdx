# Solana 소개 (Introduction to Solana)

Solana에서 구축하기 전에, Solana를 독특하게 만드는 몇 가지 근본적인 개념을 이해해야 합니다. 이 가이드는 계정, 트랜잭션, 프로그램, 그리고 그들의 상호 작용을 다룹니다.

<ArticleSection name="Solana의 계정" id="accounts-on-solana" level="h2" />

Solana의 아키텍처는 계정(accounts)을 중심으로 합니다: 블록체인에 정보를 저장하는 데이터 컨테이너입니다. 계정을 파일 시스템의 개별 파일로 생각하세요. 각 파일은 특정 속성과 그것을 제어하는 소유자를 갖습니다.

모든 Solana 계정은 동일한 기본 구조를 가집니다:

```rust
pub struct Account {
    /// 계정의 lamports
    pub lamports: u64,
    /// 이 계정에 보관된 데이터
    #[cfg_attr(feature = "serde", serde(with = "serde_bytes"))]
    pub data: Vec<u8>,
    /// 이 계정을 소유한 프로그램. 실행 가능한 경우, 이 계정을 로드하는 프로그램.
    pub owner: Pubkey,
    /// 이 계정의 데이터가 로드된 프로그램을 포함하는지 여부 (이제 읽기 전용)
    pub executable: bool,
    /// 이 계정이 다음에 임대료를 지불해야 할 에포크
    pub rent_epoch: Epoch,
}
```

모든 계정은 base58로 인코딩된 문자열(예: `14grJpemFaf88c8tiVb77W7TYg2W3ir6pfkKz3YjhhZ5`)로 표시되는 고유한 32바이트 주소를 가집니다. 이 주소는 블록체인에서 계정의 식별자 역할을 하며 특정 데이터를 찾는 방법입니다.

계정은 최대 10 MiB의 데이터를 저장할 수 있으며, 여기에는 실행 가능한 프로그램 코드나 프로그램별 데이터가 포함될 수 있습니다.

모든 계정은 "임대료 면제(rent-exempt)"가 되기 위해 데이터 크기에 비례하는 lamport 예치금이 필요합니다. "임대료"라는 용어는 역사적인 것으로, 원래는 매 에포크마다 계정에서 lamport가 차감되었지만, 이 기능은 이제 비활성화되었습니다. 오늘날 예치금은 환불 가능한 보증금처럼 작동합니다. 계정이 데이터 크기에 맞는 최소 잔액을 유지하는 한, 임대료 면제 상태를 유지하며 영구적으로 지속됩니다. 더 이상 계정이 필요하지 않으면 닫고 이 예치금을 전액 회수할 수 있습니다.

모든 계정은 프로그램에 의해 소유되며, 오직 소유 프로그램만이 계정의 데이터를 수정하거나 lamport를 인출할 수 있습니다. 그러나 누구나 계정의 lamport 잔액을 늘릴 수 있는데, 이는 프로그램 자체를 호출하지 않고도 운영 자금을 조달하거나 임대료를 지불하는 데 유용합니다.

서명 권한은 소유권에 따라 다르게 작동합니다. 시스템 프로그램(System Program)이 소유한 계정은 자체 데이터를 수정하거나, 소유권을 이전하거나, 저장된 lamport를 회수하기 위해 트랜잭션에 서명할 수 있습니다. 소유권이 다른 프로그램으로 이전되면, 여러분이 여전히 개인 키를 가지고 있더라도 그 프로그램이 계정에 대한 완전한 제어권을 얻습니다. 이 제어권 이전은 영구적이며 되돌릴 수 없습니다.

### 계정 유형 (Account Types)

가장 일반적인 계정 유형은 시스템 계정(System Account)으로, lamport(SOL의 가장 작은 단위)를 저장하며 시스템 프로그램이 소유합니다. 이들은 사용자가 SOL을 주고받기 위해 직접 상호 작용하는 기본 지갑 계정 역할을 합니다.

토큰 계정(Token Accounts)은 소유권 및 토큰 메타데이터를 포함한 SPL 토큰 정보를 저장하는 특수한 목적을 수행합니다. 토큰 프로그램(Token Program)이 이 계정들을 소유하며 Solana 생태계 전반의 모든 토큰 관련 작업을 관리합니다. 토큰 계정은 _데이터 계정(Data Accounts)_입니다.

데이터 계정(Data Accounts)은 애플리케이션별 정보를 저장하며 커스텀 프로그램이 소유합니다. 이 계정들은 애플리케이션의 상태를 보유하며, 간단한 사용자 프로필부터 복잡한 금융 데이터까지 프로그램이 요구하는 대로 구조화할 수 있습니다.

마지막으로, 프로그램 계정(Program Accounts)은 Solana에서 실행되는 실행 코드를 포함하며, 스마트 컨트랙트가 있는 곳입니다. 이 계정들은 `executable: true`로 표시되며 명령어 처리와 상태 관리를 하는 프로그램의 로직을 저장합니다.

### 계정 데이터 작업하기

프로그램이 계정 데이터와 상호 작용하는 방식은 다음과 같습니다:

```rust
#[derive(BorshSerialize, BorshDeserialize)]
pub struct UserAccount {
    pub name: String,
    pub balance: u64,
    pub posts: Vec<u32>,
}

pub fn update_user_data(accounts: &[AccountInfo], new_name: String) -> ProgramResult {
    let user_account = &accounts[0];
    
    // 기존 데이터 역직렬화
    let mut user_data = UserAccount::try_from_slice(&user_account.data.borrow())?;
    
    // 데이터 수정
    user_data.name = new_name;
    
    // 다시 계정으로 직렬화
    user_data.serialize(&mut &mut user_account.data.borrow_mut()[..])?;
    
    Ok(())
}
```

기록을 단순히 삽입하는 데이터베이스와 달리, Solana 계정은 사용하기 전에 명시적으로 생성하고 자금을 조달해야 합니다.

<ArticleSection name="Solana의 트랜잭션" id="transactions-on-solana" level="h2" />

Solana 트랜잭션은 여러 명령어를 포함할 수 있는 원자적(atomic) 작업입니다. 트랜잭션 내의 모든 명령어는 함께 성공하거나 함께 실패합니다: 부분 실행은 없습니다.

트랜잭션의 구성 요소:
- 명령어 (Instructions): 수행할 개별 작업
- 계정 (Accounts): 각 명령어가 읽거나 쓸 특정 계정들
- 서명자 (Signers): 트랜잭션을 승인하는 계정들

```rust
Transaction {
    instructions: [
        // 명령어 1: SOL 이체
        system_program::transfer(from_wallet, to_wallet, amount),
        
        // 명령어 2: 사용자 프로필 업데이트  
        my_program::update_profile(user_account, new_name),
        
        // 명령어 3: 활동 로깅
        my_program::log_activity(activity_account, "transfer", amount),
    ],
    accounts: [from_wallet, to_wallet, user_account, activity_account]
    signers: [user_keypair],
}
```

### 트랜잭션 요구 사항 및 수수료

트랜잭션은 총 1,232 바이트로 제한되어 있어 포함할 수 있는 명령어와 계정의 수를 제한합니다.

트랜잭션 내의 각 명령어는 세 가지 필수 구성 요소를 필요로 합니다: 호출할 프로그램 주소, 명령어가 읽거나 쓸 모든 계정, 그리고 함수 인수와 같은 추가 데이터입니다.

명령어는 트랜잭션 내에서 지정한 순서대로 순차적으로 실행됩니다.

모든 트랜잭션은 검증인이 트랜잭션을 처리하는 것에 대한 보상으로 서명당 5,000 lamport의 기본 수수료를 부과합니다.

또한 현재 리더가 트랜잭션을 빨리 처리할 가능성을 높이기 위해 선택적 우선순위 수수료(prioritization fee)를 지불할 수도 있습니다. 이 우선순위 수수료는 컴퓨팅 유닛 제한에 컴퓨팅 유닛 가격(마이크로-lamport 단위)을 곱하여 계산됩니다.

```
prioritization_fee = compute_unit_limit × compute_unit_price
```

> 트랜잭션 수수료를 지불하는 계정은 지불을 적절히 승인할 수 있도록 시스템 프로그램이 소유해야 합니다.

<ArticleSection name="Solana의 프로그램" id="programs-on-solana" level="h2" />

Solana의 프로그램은 근본적으로 상태가 없습니다(stateless). 즉, 함수 호출 사이에 내부 상태를 유지하지 않습니다. 대신 계정을 입력으로 받고, 그 계정 내의 데이터를 처리하고, 수정된 결과를 반환합니다.

이러한 상태 없는 설계는 예측 가능한 동작을 보장하고 강력한 구성 가능성 패턴을 가능하게 합니다.

프로그램 자체는 호출 시 실행되는 컴파일된 바이너리 코드를 포함하는 `executable: true`로 표시된 특수 계정에 저장됩니다.

사용자는 필요한 계정 데이터와 매개변수로 특정 프로그램 함수를 대상으로 하는 특정 명령어를 포함한 트랜잭션을 전송하여 이러한 프로그램과 상호 작용합니다.

```rust
use solana_program::prelude::*;

#[derive(BorshSerialize, BorshDeserialize)]
pub struct User {
    pub name: String,
    pub created_at: i64,
}

pub fn create_user(
    accounts: &[AccountInfo],
    name: String,
) -> ProgramResult {
    let user_account = &accounts[0];
    
    let user = User {
        name,
        created_at: Clock::get()?.unix_timestamp,
    };
    
    user.serialize(&mut &mut user_account.data.borrow_mut()[..])?;
    Ok(())
}
```

프로그램은 지정된 업그레이드 권한(upgrade authority)에 의해 업데이트될 수 있어, 개발자가 배포 후 버그를 수정하고 기능을 추가할 수 있습니다. 그러나 이 업그레이드 권한을 제거하면 프로그램이 영구적으로 불변하게 되어, 사용자에게 코드가 절대 변경되지 않을 것이라는 보장을 제공합니다.

투명성과 보안을 위해, 사용자는 검증된 빌드를 통해 온체인 프로그램이 공개 소스 코드와 일치하는지 확인할 수 있으며, 배포된 바이트코드가 게시된 소스와 정확히 일치함을 보장할 수 있습니다.

<ArticleSection name="프로그램 파생 주소 (PDAs)" id="program-derived-addresses" level="h2" />

PDA(Program Derived Addresses)는 강력한 프로그래밍 패턴을 가능하게 하는 결정론적으로 생성된 주소입니다. 시드(seeds)와 프로그램 ID를 사용하여 생성되며 대응하는 개인 키가 없는 주소를 생성합니다.

PDA는 커스텀 시드, 오프 커브(off-curve)임을 보장하기 위한 범프(bump) 값, 이 PDA를 소유할 프로그램 ID, 그리고 상수 마커를 포함한 특정 입력과 함께 `SHA-256` 해싱을 사용합니다.

해시가 온 커브(on-curve) 주소를 생성하면(약 50%의 확률로 발생), 시스템은 오프 커브 결과를 찾을 때까지 범프 255에서 254, 253 등으로 내려가며 반복합니다.

```rust
use solana_nostd_sha256::hashv;

const PDA_MARKER: &[u8; 21] = b"ProgramDerivedAddress";

let pda = hashv(&[
    seed_data.as_ref(),    // 커스텀 시드
    &[bump],               // 오프 커브 보장 범프
    program_id.as_ref(),   // 이 PDA를 소유하는 프로그램
    PDA_MARKER,
]);
```

### 이점

PDA의 결정론적 특성은 주소를 저장할 필요를 없앱니다: 필요할 때마다 동일한 시드에서 다시 생성할 수 있습니다.

이는 온체인에서 해시맵 구조처럼 작동하는 예측 가능한 주소 지정 체계를 만듭니다. 더 중요한 것은, 프로그램이 자신의 PDA를 위해 서명할 수 있어 개인 키를 노출하지 않고도 자율적인 자산 관리가 가능하다는 것입니다:

```rust
let seeds = &[b"vault", user.as_ref(), &[bump]];

invoke_signed(
    &transfer_instruction,
    &[from_pda, to_account, token_program],
    &[&seeds[..]], // 프로그램이 PDA 제어를 증명함
)?;
```

<ArticleSection name="교차 프로그램 호출 (CPI)" id="cross-program-invocation" level="h2" />

CPI(Cross Program Invocation)는 프로그램이 동일한 트랜잭션 내에서 다른 프로그램을 호출할 수 있게 하여, 외부 조정 없이 여러 프로그램이 원자적으로 상호 작용할 수 있는 진정한 구성 가능성(composability)을 생성합니다.

이를 통해 개발자는 기능을 처음부터 다시 구축하는 대신 기존 프로그램을 결합하여 복잡한 애플리케이션을 구축할 수 있습니다.

CPI는 일반 명령어와 동일한 패턴을 따르며, 대상 프로그램, 필요한 계정, 명령어 데이터를 지정해야 하는데, 주된 차이점은 다른 프로그램 내부에서 수행될 수 있다는 것입니다.

호출하는 프로그램은 흐름에 대한 제어를 유지하면서 특정 작업을 전문 프로그램에 위임합니다:

```rust
let cpi_accounts = TransferAccounts {
    from: source_account.clone(),
    to: destination_account.clone(), 
    authority: authority_account.clone(),
};

let cpi_ctx = CpiContext::new(token_program.clone(), cpi_accounts);
token_program::cpi::transfer(cpi_ctx, amount)?;
```

### 제약 조건 및 기능

원래 트랜잭션 서명자는 CPI 체인 전체에서 권한을 유지하여, 프로그램이 사용자 대신 원활하게 행동할 수 있게 합니다.

그러나 무한 재귀를 방지하기 위해 프로그램은 최대 4단계 깊이(`A → B → C → D`)까지만 CPI를 수행할 수 있습니다. 프로그램은 또한 `CpiContext::new_with_signer`를 사용하여 CPI에서 자신의 PDA를 위해 서명할 수 있어, 정교한 자율 작업을 가능하게 합니다.

이러한 구성 가능성은 단일 원자적 트랜잭션 내에서 여러 프로그램에 걸친 복잡한 작업을 가능하게 하여, Solana 애플리케이션을 매우 모듈화되고 상호 운용 가능하게 만듭니다.
