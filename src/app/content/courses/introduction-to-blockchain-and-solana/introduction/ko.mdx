# 블록체인 소개 (Introduction to Blockchain)

![Introduction to Blockchain](/graphics/course-banners/introduction-to-blockchain-and-solana.png)

아마 블록체인을 "디지털 화폐"나 "인터넷의 미래"라고 설명하는 것을 들어보셨을 것입니다. 이러한 설명은 핵심을 완전히 놓치고 있습니다.

블록체인은 분산 시스템(Distributed Systems)입니다. 서로 신뢰하지 않는 컴퓨터들의 네트워크가 공유된 데이터에 대해 합의해야 하는 시스템이죠. 이 코스는 제1원칙부터 블록체인을 가르칩니다: 블록체인이 해결하는 분산 시스템 문제들, 이를 해결하는 방법, 그리고 왜 그 트레이드오프가 중요한지에 대해서 말이죠.

왜 분산 시스템을 구축하는 것이 컴퓨터 과학에서 가장 어려운 문제 중 하나인지 이해하는 것부터 시작해 봅시다.

<ArticleSection name="분산 시스템" id="distributed-systems" level="h2" />

대부분의 사람들은 하나의 컴퓨터에서 여러 대로 확장하는 것이 단지 "같은 것을 더 많이" 하는 것이라고 생각합니다. 그것은 한 사람을 조정하는 것이 서로 다른 시간대에 있고 항상 연락이 닿지 않을 수도 있는 천 명의 사람들을 조정하는 것과 같다고 생각하는 것과 같습니다.

단일 컴퓨터에서 코드를 작성할 때, 여러분은 예측 가능한 세상에 살고 있습니다:
- 작업은 즉시 성공하거나 실패합니다
- 데이터는 읽기 사이에 미스터리하게 변하지 않습니다
- 시간은 일관되게 앞으로 흐릅니다
- 무언가를 저장하면, 실제로 저장됩니다

간단한 은행 시스템을 예로 들어봅시다. Alice에서 Bob으로 $100를 이체하는 것은 이 경우 매우 쉽습니다:

```python
def transfer(from_account, to_account, amount):
    if from_account.balance >= amount:
        from_account.balance -= amount
        to_account.balance += amount
        return "Transfer successful"
    return "Insufficient funds"
```

이것은 완벽하게 작동합니다... 확장해야 할 때까지는요.

은행이 하나의 컴퓨터가 처리할 수 있는 범위를 넘어서 성장하여, 이제 계좌를 서로 다른 데이터베이스에 균등하게 분할합니다:
- 서버 A: 계좌 1 ~ 1,000,000
- 서버 B: 계좌 1,000,001 ~ 2,000,000
- 서버 C: 계좌 2,000,001 ~ 3,000,000

이제 Alice(서버 A)가 Bob(서버 B)에게 $100를 보내려고 합니다. 그 간단한 이체는 다음과 같이 변합니다:

```python
def distributed_transfer(alice_server, bob_server, amount):
    # 서버 A에서 Alice의 잔액 확인
    if alice_server.get_balance("alice") >= amount:
        alice_server.deduct("alice", amount)    # 1단계
        bob_server.add("bob", amount)           # 2단계
        return "Transfer successful"
    return "Insufficient funds"
```
여전히 간단해 보이나요? 여기서 잘못될 수 있는 것들은 다음과 같습니다:
- 네트워크 분할(Network Partition): 1단계 직후 2단계 전에 서버 간의 연결이 끊어집니다. Alice의 $100는 디지털 허공으로 사라집니다.
- 서버 충돌(Server Crash): 서버 B가 "돈 추가" 명령을 받은 후 처리를 확인하기 전에 충돌합니다. Bob이 돈을 받았나요? 아무도 모릅니다.
- 경쟁 상태(Race Conditions): Alice로부터의 두 이체가 동시에 발생합니다. 둘 다 그녀의 $100 잔액을 확인하고, 자금이 충분하다고 보고, 둘 다 진행합니다. Alice는 이제 그녀가 가지고 있지도 않은 $100를 사용했습니다.

### CAP 이론 (CAP Theorem)

1999년, 컴퓨터 과학자 Eric Brewer는 CAP 이론을 정립했습니다. 이는 어떤 분산 시스템도 다음 세 가지 속성 중 최대 두 가지만 보장할 수 있다는 것입니다:
- 일관성 (Consistency, C): 모든 서버는 항상 동일한 데이터를 보여줍니다. 서버 A에서 Alice의 잔액이 변경되면, 다른 모든 서버도 즉시 이를 반영합니다.
- 가용성 (Availability, A): 서버가 충돌하더라도 시스템은 계속 작동합니다. 서버 A가 다운되더라도 사용자는 서버 B와 C를 통해 계좌에 접근할 수 있습니다.
- 분할 내성 (Partition Tolerance, P): 시스템은 서버를 고립된 그룹으로 나누는 네트워크 실패에도 살아남습니다.

네트워크 분할은 불가피하므로(케이블이 끊기고, 라우터가 고장 나고, 데이터 센터가 전력을 잃으므로), 우리는 분할 내성을 반드시 보장해야 합니다. 이는 결국 일관성 또는 가용성 중 하나를 선택해야 함을 의미합니다.

전통적인 은행 시스템은 보통 일관성 + 분할 내성 (CP 시스템)을 선택합니다. 그들은 잘못된 계좌 잔액을 보여주는 것보다 차라리 멈추는 것을 선호합니다.

소셜 미디어 플랫폼은 종종 가용성 + 분할 내성 (AP 시스템)을 선택합니다. 그들은 친구들이 즉시 볼 수 없더라도 게시글을 올릴 수 있게 하는 것(완전히 게시를 못 하게 하는 것보다)을 선호합니다.

### 비잔틴 장군 문제 (The Byzantine Generals Problem)

CAP 이론 외에도, 대부분의 분산 시스템은 참여자가 정직하다고 가정합니다: 그들은 실패하거나 연결이 끊길 수 있지만, 서로를 적극적으로 속이지는 않을 것입니다. 이 가정은 참여자가 악의적일 수 있을 때 무너집니다.

1982년 컴퓨터 과학자들이 정립한 비잔틴 장군 문제는 이 도전을 보여줍니다:

여러분은 요새화된 도시를 공격할 계획인 비잔틴 장군입니다. 도시 주변에 여러 동맹 장군들이 위치해 있고, 각자 자신의 군대를 지휘합니다. 성공하려면 동시에 공격하도록 조율해야 합니다. 일부는 공격하고 다른 이들은 후퇴하면, 공격하는 군대는 전멸할 것입니다.

오직 전령을 통해서만 소통하며, 일부 장군은 공격이 실패하기를 원하는 배신자일 수 있습니다. 배신자들은:
- 일부 장군에게는 "공격" 메시지를, 다른 장군에게는 "후퇴" 메시지를 보낼 수 있습니다
- 충직한 장군들의 메시지가 전달될 때 수정할 수 있습니다
- 다른 배신자들과 조율하여 혼란을 극대화할 수 있습니다

충직한 장군과 배신자를 구별할 수 없고 통신 채널을 신뢰할 수 없을 때, 어떻게 "공격" 또는 "후퇴"에 대한 합의에 도달할 수 있을까요?

이것은 불가능해 보였습니다. 수십 년 동안 컴퓨터 과학자들은 다음을 동시에 만족하는 시스템을 구축할 수 없다고 믿었습니다:
- 비잔틴 결함 허용 (악의적인 참여자들에도 불구하고 작동)
- 무허가성 (승인 없이 누구나 참여 가능)
- 탈중앙화 (중앙 권한 없음)

그러다 2008년, 스스로를 사토시 나카모토라고 부르는 누군가가 그들이 틀렸음을 증명했습니다.

### 비트코인: 최초의 블록체인

비트코인은 블록체인 기술의 최초의 실용적인 구현이었습니다. 개별 구성 요소들(암호학적 해싱, 디지털 서명, P2P 네트워크)은 이전에도 존재했지만, 사토시는 디지털 화폐의 이중 지불 문제를 해결하기 위해 이들을 처음으로 결합했습니다.

원래 비트코인 [백서](https://bitcoin.org/bitcoin.pdf)에서 불린 대로 "블록의 체인(chain of blocks)" 또는 블록체인은 마침내 분산되어 있고, 비잔틴 결함을 허용하며, 무허가성인 시스템을 동시에 만들어냈습니다.

획기적인 점은 누구를 신뢰할지 식별하려는 것이 아니라, 거짓말을 하는 것을 진실을 말하는 것보다 경제적으로 더 비싸게 만드는 것이었습니다. 작업 증명(Proof of Work)은 참여자들이 변경을 제안하기 위해 실제 계산 에너지를 소비하도록 요구함으로써 이를 달성합니다. 공격자는 공격으로 얻을 수 있는 이득보다 전기료에 더 많은 비용을 써야 할 것입니다.
