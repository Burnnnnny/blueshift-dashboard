# 유형 코스프레 (Type Cosplay)

유형 코스프레 공격은 계정 유형을 확인하지 못하는 프로그램을 악용하여 공격자가 동일한 데이터 구조를 갖지만 의도된 용도가 다른 계정으로 대체할 수 있도록 합니다. Solana는 모든 계정 데이터를 원시 바이트로 저장하므로 계정 유형을 확인하지 않는 프로그램은 `VaultConfig`를 `AdminSettings`로 처리하도록 속여 잠재적으로 치명적인 결과를 초래할 수 있습니다.

이 취약점은 구조적 모호성에서 비롯됩니다. 여러 계정 유형이 동일한 데이터 레이아웃(예: 둘 다 `owner: Pubkey` 필드 가짐)을 공유하는 경우 소유자 확인 및 데이터 검증만으로는 이를 구별하기에 충분하지 않습니다. 한 유형의 계정을 제어하는 공격자는 완전히 다른 계정 유형의 소유자로 가장하여 특정 계정 목적을 중심으로 설계된 권한 부여 로직을 우회할 수 있습니다.

구별자(계정 유형을 구별하는 고유 식별자)가 없으면 프로그램은 악의적인 행위자가 구조적 유사성과 논리적 의도 사이의 격차를 악용할 수 있는 정교한 사칭 공격에 취약해집니다.

<ArticleSection name="Anchor" id="anchor" level="h2" />

계정 소유권을 기반으로 관리자 작업을 수행하는 이 취약한 명령어를 고려하십시오:

```rust
#[program]
pub mod insecure_check{
    use super::*;
    //..

    pub fn instruction(ctx: Context<Instruction>) -> Result<()> {
        let program_account_one = ctx.accounts.program_account_one.to_account_info();
        if program_account_one.owner != ctx.program_id {
            return Err(ProgramError::IllegalOwner.into());
        }
        if ctx.accounts.program_account_one.owner != ctx.accounts.admin.key() {
            return Err(ProgramError::InvalidAccountData.into());
        }

        //..do something
    
        Ok(())

    }
        
    //..
}

#[derive(Accounts)]
pub struct Instruction<'info> {
    pub admin: Signer<'info>,
   #[account(mut)]
    /// CHECK: This account will not be checked by Anchor
    pub program_account_one: UncheckedAccount<'info>,
    #[account(mut)]
    /// CHECK: This account will not be checked by Anchor
    pub program_account_two: UncheckedAccount<'info>,

}

#[derive(AnchorSerialize, AnchorDeserialize, InitSpace)]
pub struct ProgramAccountOne {
    owner: Pubkey,
}

#[derive(AnchorSerialize, AnchorDeserialize, InitSpace)]
pub struct ProgramAccountTwo {
    owner: Pubkey,
}
```

이 코드는 안전해 보입니다. 프로그램 소유권을 확인하고 관리자 권한을 검증합니다. 그러나 치명적인 결함이 있습니다. `program_account_one`이 실제로 `ProgramAccountOne`이며 동일한 데이터 구조를 가진 다른 계정 유형이 아닌지 확인하지 않습니다.

공격자는 다음을 통해 이를 악용할 수 있습니다:
- `ProgramAccountTwo` 계정 생성 또는 제어
- 해당 계정의 데이터에 자신을 소유자로 설정
- `ProgramAccountTwo`를 `program_account_one` 파라미터로 전달
- 두 계정 유형 모두 동일한 `owner: Pubkey` 구조를 가지므로 역직렬화 성공
- 공격자는 `ProgramAccountOne` 소유자만을 위한 작업의 "관리자"가 됨

Solana는 구별자를 사용하여 이 문제를 해결합니다:
- Anchor의 8바이트 구별자(기본값): 계정 이름에서 파생되며 #[account]로 표시된 계정에 자동으로 추가됩니다. (anchor `0.31.0`부터 "사용자 지정" 구별자 구현 가능)
- 길이 기반 구별: 토큰 프로그램이 Token 계정과 Mint 계정을 구별하는 데 사용합니다(Token2022는 이제 명시적 구별자를 사용함).

가장 간단한 수정은 Anchor의 내장 유형 검증을 사용하는 것입니다:

```rust
#[derive(Accounts)]
pub struct Instruction<'info> {
    pub admin: Signer<'info>,
   #[account(mut)]
    /// CHECK: This account will not be checked by Anchor
    pub program_account_one: Account<'info, ProgramAccountOne>,
    #[account(mut)]
    /// CHECK: This account will not be checked by Anchor
    pub program_account_two: Account<'info, ProgramAccountTwo>,

}

#[account]
pub struct ProgramAccountOne {
    owner: Pubkey,
}

#[account]
pub struct ProgramAccountTwo {
    owner: Pubkey,
}
```

또는 사용자 지정 검증의 경우 명시적 구별자 검사를 추가할 수 있습니다:

```rust
pub fn instruction(ctx: Context<Instruction>) -> Result<()> {
    let program_account_one = ctx.accounts.program_account_one.to_account_info();
    if program_account_one.owner != ctx.program_id {
        return Err(ProgramError::IllegalOwner.into());
    }
    if ctx.accounts.program_account_one.owner != ctx.accounts.admin.key() {
        return Err(ProgramError::InvalidAccountData.into());
    }
    let data = program_account_one.data.borrow();
    // ProgramAccountOne의 구별자가 8바이트라고 가정
    let discriminator = &data[..8];
    if discriminator != ProgramAccountOne::DISCRIMINATOR {
        return Err(ProgramError::InvalidAccountData.into());
    }

    //..do something

    Ok(())
}
```

Pinocchio에서는 구별자 검사를 수동으로 구현합니다:

```rust
let account_data = self.accounts.program_account.try_borrow_data()?;

if account_data[0] != DISCRIMINATOR {
    return Err(ProgramError::AccountAlreadyInitialized.into());
}
```
