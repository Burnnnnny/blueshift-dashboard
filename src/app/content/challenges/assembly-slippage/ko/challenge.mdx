# 어셈블리 슬리피지 (Assembly Slippage)

이 유닛에서는 sBPF 어셈블리를 사용하여 기본적인 슬리피지 확인 명령어를 만들 것입니다. 명령어 배열의 마지막 인덱스에 이러한 명령어를 포함함으로써 스마트 컨트랙트 버그나 악의적인 비트 반전(bit flip) 컨트랙트에 대한 최후의 수단으로 추가 보호를 만들 수 있습니다.

어셈블리를 슬리피지 확인의 이상적인 후보로 만드는 몇 가지 속성이 있습니다:

- 단일의, 제한된 사용 사례
- 서명자/계정 확인을 수행할 필요가 없음
- 보안을 향상시킬 뿐임

어셈블리 프로그램을 작성하는 방법에 익숙하지 않은 경우 [어셈블리 소개 과정](/ko/courses/introduction-to-assembly)을 따르세요.

<ArticleSection name="프로그램 설계" id="program-design" level="h2" />

우리 프로그램은 간단하지만 중요한 작업을 수행합니다. 즉, 트랜잭션을 진행하기 전에 토큰 계정이 충분한 잔액을 가지고 있는지 검증하는 것입니다. 이 패턴은 AMM 스왑에서 대출 프로토콜에 이르기까지 DeFi의 모든 곳에서 나타납니다.

프로그램이 예상하는 것:
- 계정 배열의 단일 SPL 토큰 계정
- 명령어 데이터의 8바이트 금액
- 잔액 ≥ 금액이면 성공을 반환하고, 그렇지 않으면 오류를 반환

<ArticleSection name="메모리 오프셋" id="memory-offsets" level="h2" />

sBPF 프로그램은 연속적인 메모리 영역으로 계정 데이터를 받습니다. 이 상수들은 바이트 오프셋을 정의합니다. 우리 프로그램이 단일 계정만 받고 그것이 SPL 토큰 계정이 될 것이라고 가정하면 다음 오프셋을 정적으로 파생할 수 있습니다:

```sbpf
.equ TOKEN_ACCOUNT_BALANCE, 0x00a0
.equ MINIMUM_BALANCE, 0x2918
```

- `TOKEN_ACCOUNT_BALANCE (0x00a0)`: SPL 토큰 계정 데이터의 잔액 필드를 가리킵니다. 토큰 계정은 잔액(8바이트, 리틀 엔디안)이 오프셋 160에 위치하는 표준 레이아웃을 따릅니다.
- `MINIMUM_BALANCE (0x2918)`: Solana가 명령어 데이터 페이로드를 배치하는 위치를 찾습니다. 이 오프셋은 런타임의 계정 정보 구조의 일부입니다.

> [sbpf.xyz](https://sbpf.xyz)에서 도구를 사용하여 오프셋을 생성할 수 있습니다.

메모리 레이아웃을 추상화하는 고급 언어와 달리 어셈블리에서는 모든 데이터가 어디에 있는지 정확히 알아야 합니다.

<ArticleSection name="진입점 및 초기 검증" id="entrypoint-and-validations" level="h2" />

```sbpf
.globl entrypoint
entrypoint:
    ldxdw r3, [r1+MINIMUM_BALANCE]      // Get amount from IX data
    ldxdw r4, [r1+TOKEN_ACCOUNT_BALANCE] // Get balance from token account
```

모든 sBPF 프로그램은 글로벌 `.entrypoint` 심볼에서 시작합니다. Solana 런타임은 레지스터 `r1`을 통해 계정 및 명령어 데이터를 제공합니다.

`ldxdw` 명령어는 메모리에서 8바이트(double word, `dx`) 값을 레지스터로 로드(`ldx`)합니다. 일어나는 일은 다음과 같습니다:
- `ldxdw r3, [r1+MINIMUM_BALANCE]`: 필요한 금액이 포함된 메모리 주소를 계산합니다. 값이 `r3`에 로드됩니다.
- `ldxdw r4, [r1+TOKEN_ACCOUNT_BALANCE]`: 토큰 계정의 잔액 필드를 가리킵니다. 이 64비트 값은 `r4`에 위치합니다.

두 작업 모두 무복사(zero-copy)입니다. 직렬화 오버헤드 없이 계정 데이터에서 직접 읽습니다.

<ArticleSection name="조건부 로직 및 분기" id="conditional-logic-and-branching" level="h2" />

```sbpf
jge r3, r4, end         // Skip to exit if balance is valid
```

`jge` (크거나 같으면 점프) 명령어는 `r3`(필요 금액)를 `r4`(사용 가능 잔액)와 비교합니다. `r3 >= r4`이면 `end` 레이블로 점프합니다. 조기 반환과 같습니다.

조건이 실패하면 실행은 오류 처리 경로로 계속됩니다. 이 조건부 분기 패턴은 어셈블리가 if/else 로직을 구현하는 방식입니다.

<ArticleSection name="오류 처리 및 로깅" id="error-handling-and-logging" level="h2" />

```sbpf
lddw r1, e              // Load error message address
lddw r2, 17             // Load length of error message  
call sol_log_           // Log out error message
lddw r0, 1              // Return error code 1
```

검증이 실패하면 종료하기 전에 사람이 읽을 수 있는 오류를 기록합니다:
- `lddw`는 즉시 값, 이 경우 `.rodata` 섹션에 있는 오류 문자열의 주소와 그 길이("Slippage exceeded"의 경우 17바이트)를 로드합니다.
- `call sol_log_`는 Solana의 로깅 시스템 호출을 호출합니다. 런타임은 메모리에서 메시지를 읽고 트랜잭션 로그에 추가합니다.
- 그런 다음 `r0`에 `1`을 로드하여 프로그램 실패를 알립니다. 런타임은 트랜잭션을 중단하고 이 오류 코드를 반환합니다.

<ArticleSection name="프로그램 종료" id="program-termination" level="h2" />

```sbpf
end:
    exit
```

`exit` 명령어는 프로그램 실행을 종료하고 제어를 Solana 런타임으로 반환합니다. `r0`의 값은 프로그램의 종료 코드(성공의 경우 0, 오류의 경우 0이 아닌 값)가 됩니다.

자동 정리 기능이 있는 고급 언어와 달리 어셈블리 프로그램은 명시적으로 종료해야 합니다. 코드 끝에서 떨어지는 것은 정의되지 않은 동작입니다.

## 읽기 전용 데이터 (Read-only Data)

```sbpf
.rodata
    e: .ascii "Slippage exceeded"
```

`.rodata`(읽기 전용 데이터) 섹션에는 오류 메시지 문자열이 포함되어 있습니다.

<ArticleSection name="결론" id="conclusion" level="h2" />
  
이 작은 프로그램은 Rust가 패스 케이스에서 `4 CU`, 실패 케이스에서 `6 CU`, 오류 메시지를 기록하는 실패 케이스에서 `106 CU`로 수십 개의 CU가 걸릴 수 있는 작업을 수행합니다.

이점은 가장 낮은 수준에서 메모리 레이아웃, 호출 규칙 및 오류 처리를 이해해야 한다는 것입니다. 그러나 성능이 중요한 작업의 경우 이점은 종종 노력을 정당화합니다.
